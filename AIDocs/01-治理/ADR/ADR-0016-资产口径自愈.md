# ADR-0016: 修复不得依赖人工动作——资产口径在编译周期内自愈

> **状态**：已采纳
> **日期**：2026-10-10
> **决策者**：扣丢桑（报「还是不好使，武器跟随移动但英雄没有跟随走」）
> **影响范围**：`Editor`（新增 `GlyphMaterialSelfHeal`、`GlyphAssetBuilder` 增对账入口）、`Data/Materials/Mat_Glyph_Hero.mat`、`AGENTS.md` 踩坑录
> **关联 Spec**：无（事故复盘 + 机制补强）

---

## 背景（Context）

ADR-0015 判定「英雄字块不动」的根因是：英雄材质指向了给 `DrawMeshInstancedIndirect` 用的 `GlyphInstanced` 着色器。**判断没错，修法也没错**——新增 `GlyphFlat`，并把选型收口进 `GlyphAssetBuilder.EnsureMaterial`。

但修完之后用户报「**还是不好使**」。这次取证（全部文件级，未用运行时探活）：

| 证据 | 内容 |
|------|------|
| `Mat_Glyph_Hero.mat` | 仍写着 `guid 63c1aada…`（`GlyphInstanced`），且带着只有 instanced 版才有的 `_GlyphSize: 1.1` |
| 该文件 mtime | `2026-10-07 23:49:35` —— 事故当天**一次都没被写过** |
| `Editor.log` | `GlyphFlat.shader` 于 `00:29:41` 导入并编译成功（`ok=1`）；**没有任何** `[GlyphAssetBuilder]` 重建记录；无 `Shader error`、无 `error CS` |
| 新截图 | 金橙字形实测 17×14 px ↔ 1.1 m（与一个「兵」字等大），随相机移动**不动**；武器是读 Transform 的 `Unlit/Color`，正常跟随、朝向会转（上一张横条，这张 3×34 竖条）；全图零品红像素 → 排除着色器编译失败 |

也就是：**代码对、着色器对、编译干净，唯独那张材质资产没有被重建。**

根因是机制性的，不是疏忽：**着色器是存在 `.mat` 资产文件里的一个持久字段，C# 改了它不会跟着变。** 上一轮的修法只把「让资产变对的办法」放进了一个 `[MenuItem]`——而菜单是给人点的，人不会记得。于是「修法正确」与「问题被修好」之间断了一环。

这一环必须补，否则同一类坑会换个形式再来：`manifest.json` 的包版本、`ProjectSettings` 的开关、`.meta` 的导入参数——全都是「资产上的字段」。

---

## 备选方案（Options）

| 方案 | 做法 | 判断 |
|------|------|------|
| A. 不改机制，只在文档里提醒「记得跑菜单」 | 靠纪律 | ❌ 这正是失败的那一环。文档不会在出错的时刻拦住任何人，而这类失配**静态检查全都过**，只在 Play 时才暴露 |
| B. 运行时自愈：`HeroView.Awake` 检查 `sharedMaterial.shader`，不对就换材质 | 表现层自己保证画对 | ❌ 表现层被迫知道「着色器选型」（越过宪法 §3.1）；用 `renderer.material` 会在运行时生成材质实例、Inspector 冒出 `Mat_Glyph_Hero (Instance)`；而且它**掩盖问题**——资产仍然是错的，只是这次碰巧绕过 |
| C. `AssetPostprocessor.OnPostprocessAllAssets` 里对账 | 资产导入时触发 | ⚠️ 只在**该资产被导入**时触发。而这次的失败恰好是「资产没被导入过」（它没变）。触发条件与失败条件不重合 |
| D. `[InitializeOnLoad]` + `EditorApplication.delayCall` 做对账 | 每次脚本编译完（域重载）把资产跟代码约定比一次 | ✅ 触发条件与失败条件重合：**有代码变更 → 必然重编译 → 必然重载域 → 必然对账一次**。改动代码的人必然触发它，而那正是需要它的时刻 |
| E. 直接手改资产 YAML，不写机制 | 一次性 | ✅ 本次已做（改 guid + 补 `_Flash`），但它防不了复发 → 与 D 并用 |

---

## 决策（Decision）

**D + E 并用：先手改资产让它立刻可用，再加自愈钩子防复发。**

### 1. 窄入口 `GlyphAssetBuilder.AlignMaterialShader(name, instancing)`

做的是**对账**，不是重建：

- 材质不存在 → 返回 `false`，**不创建**（凭空生资产应该是显式动作，不该在编辑器启动时发生）；
- 着色器还没导入完（`Shader.Find` 为 `null`，刚新增 `.shader` 时的常态）→ 返回 `false`，**跳过**，等下一次域重载；
- 口径一致（shader + `enableInstancing` 都对）→ 返回 `false`，**不写盘**；
- 只在真的不一致时改，返回 `true`。

刻意不碰贴图 / 颜色 / `_Cutoff`——那些属于外观，交给显式的 `Rebuild Glyph Assets`。**只对账「渲染通道口径」这一件事**，边界清楚。

### 2. `Editor/GlyphMaterialSelfHeal`：钩在域重载上

```csharp
[InitializeOnLoad]
internal static class GlyphMaterialSelfHeal
{
    static GlyphMaterialSelfHeal()
    {
        // 静态构造在域重载中途跑，此时资产数据库还在重建索引；delayCall 等空闲再动
        EditorApplication.delayCall += Heal;
    }
}
```

`Heal()` 对两张字建材质各调一次 `AlignMaterialShader`；只要有一张被纠，就 `AssetDatabase.SaveAssets()` 并 `Debug.Log`（写明「反复出现说明有别的脚本在写这些材质」）。

### 3. 本次同时手改 `Mat_Glyph_Hero.mat`

- `m_Shader` guid：`63c1aada…`（`GlyphInstanced`）→ `782e64cf84cee83499918b124ce8e2db`（`GlyphFlat`）；
- 删掉 `_GlyphSize: 1.1`（instanced 版专有参数，留在单实例材质上是误导），补 `_Flash: 0`。

## 后果（Consequences）

### 正面

- **「代码改了但没生效」这一类故障被机制性消灭**：只要动过 C#，编译就会发生，对账就会发生。
- **失败可见**：自愈触发时打日志。下次同类问题能在 Console 里一眼看到，不必再靠像素反推。
- **对账入口很窄**：只碰 shader 与 `enableInstancing` 两项，不会意外覆盖美术调过的颜色。

### 负面 / 需要接受的代价

- **行为发生在 `[InitializeOnLoad]` 里**，读 `HeroView` 是找不到它的——必须在 `AGENTS.md` 与本 ADR 里留指路（已做）。
- **每次域重载多两次 `LoadAssetAtPath` + `Shader.Find`**：微秒级，但它是「每次」。
- **只能治「口径」类失配**。将来若代码改了**颜色**的默认值，自愈不会管（那是外观不是口径）——这条边界要靠人守。
- **手改资产 YAML 有版本风险**：Unity 重新导入时会按 shader 的 `Properties` 补齐/清理属性，格式本身稳定；若 Unity 换了材质序列化格式，手写的部分要跟着改。

### 后续动作

- [ ] 把「口径对账」推广到 `manifest.json` / `ProjectSettings` 等其他「代码约定 vs 资产字段」的地方（目前只做了字形材质）
- [ ] 加一个 Editor 测试，断言两张字建材质的 shader 与 `GlyphAssetBuilder` 的约定一致——把对账也纳入自检，而不是只在编辑器启动时默默修
- [ ] 英雄出生表现 / 兵死亡碎裂帧（沿用 ADR-0015 的后续动作，本次未动）

## 复核条件（何时重新评估）

- **Unity 提供「资产字段随代码自动同步」的原生机制** → 退回用原生，删掉自愈钩子
- **出现第二处需要自愈的资产口径** → 复核该抽成通用工具，而不是复制一个 `XXXSelfHeal`
- **自愈日志开始反复出现** → 说明有别的代码在写这些材质，先查写方，别把日志当噪音
