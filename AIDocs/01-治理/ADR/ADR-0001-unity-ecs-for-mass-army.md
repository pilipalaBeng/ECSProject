# ADR-0001: 采用 Unity ECS/DOTS 作为战斗逻辑层

> **状态**：已采纳
> **日期**：2026-10-07
> **决策者**：扣丢桑（AI 提供分析与建议）
> **影响范围**：整体架构、程序集划分、编码规范、招人/协作

---

## 背景（Context）

项目目标是"曹操十万大军"级别的割草体验——同屏需要数千到上万敌方单位持续移动、受击、死亡。
若用传统 GameObject + MonoBehaviour 方案，万级对象的 Transform 更新与组件开销会直接压垮主线程。

约束条件：
- 单人（+AI 代理）开发，工程成本敏感
- 表现层需要大量 UI/特效，但战场文字不能走 UI 组件
- 团队规模小，架构学习成本是真实代价

---

## 备选方案（Options）

| 方案 | 优点 | 缺点 | 成本 |
|------|------|------|------|
| A. 纯 GameObject + 对象池 | 开发快、调试直观、生态成熟 | 万级对象必然崩；Transform 开销无法回避 | 低（但达不到目标） |
| B. **全 ECS/DOTS 逻辑层 + 自定义 instanced 表现层** | 万级实体可跑；Burst+Job 性能好；数据驱动天然适合数值调优 | 学习曲线陡；UI 集成需绕开；调试工具弱 | 中高 |
| C. OOP 逻辑 + Burst/Job 只做数学加速 | 折中，保留 GameObject 便利 | 对象开销仍在；两套心智模型并存 | 中 |
| D. 换引擎 / 用现成海量单位框架 | — | 放弃 Unity 生态与既有经验 | 高 |

---

## 决策（Decision）

**选择方案 B**，理由：

1. 实体规模目标（5,500-16,500，见 C1）明确落在 ECS 甜区，这是 DOTS 存在的理由。若规模只有几百，方案 A 更优——但那不是本项目。
2. 数据驱动（component 即数据）天然契合肉鸽的数值调优需求：改数值不动代码结构。
3. 表现层通过自定义 instanced 渲染绕开 UI 组件，**规避了 DOTS 最出名的 UI 集成痛点**（见 ADR-0003）。

---

## 后果（Consequences）

### 正面

- 万级实体在 Burst 编译下可跑（具体帧率待实测，见 C1.7）
- 逻辑与表现彻底分离，表现层可独立替换/优化
- 数值全部数据化，便于批量验算与平衡

### 负面 / 需要接受的代价

- 开发速度较 OOP 慢（同等功能代码量约 2-3 倍）
- 调试成本高：Entity debugger 不如 Inspector 直观
- 协作门槛：接手者需懂 ECS；AI 代理在 ECS 代码上的出错率高于普通 C#
- Entities 版本与 Unity 2022.3 LTS 的兼容矩阵待确认（U4）

### 后续动作

- [ ] 确认 Entities 版本与 Unity 版本组合（U4）
- [ ] 搭建最小 ECS 工程骨架（Core/Gameplay/Presentation 三程序集）
- [ ] 性能基准：空场景 + 12,000 实体移动，记录帧时间（C1.7）

---

## 复核条件（何时重新评估）

出现以下任一情况应重新审视：

- 实体规模目标下调到 **<2,000**（此时 ECS 收益消失，方案 A 更优）
- Entities 包在目标 Unity 版本上出现阻断性 Bug
- 开发周期压力导致核心玩法无法在预算内完成（应优先砍玩法，而非退架构）
