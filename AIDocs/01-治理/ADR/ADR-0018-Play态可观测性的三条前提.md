# ADR-0018: Play 的可观测性有三条前提——暂停 / 失焦输入 / 已阵亡冻结

> **状态**：已采纳
> **日期**：2026-10-10
> **决策者**：扣丢桑（报「依然不会对小兵造成伤害，我 mcp 已经打开了，你自己来改吧」）
> **影响范围**：`ProjectSettings/ProjectSettings.asset`（`runInBackground: 1`）、`Presentation/HudController`（R 键重开 + 失焦提示）、`Editor/CombatSmokeTest`（自检世界裁剪的说明）、`AGENTS.md`（MCP 通道大坑段的措辞）
> **关联 Spec**：`数值预算表.md` §5（2026-10-10 第二轮故障实测）

---

## 背景（Context）

ADR-0017 之后，用户仍报：

> **依然不会对小兵造成伤害**。我 mcp 已经打开了，你自己来改吧。

这一次有 MCP，可以直读运行态。取证顺序与结论：

| 探针 | 读数 | 说明 |
|------|------|------|
| `Application.isPlaying` | `False` | 编辑器**根本不在 Play**——前几轮「看到」的是编辑器里的静态画面 |
| 进 Play 后 `CombatBalance` | `n=1`，`Reach=3.6 HalfW=1.1 PointBlank=1.8 HeroHP=200` | 配置资产读对了，ADR-0017 的数值全部生效 |
| `Heroes / Enemies / Progress` | `0 / 0`，`spawnDone=False` | `Enter()` 成功打了 `战斗就绪`，但**生成系统一帧都没跑** |
| `World.Time.ElapsedTime`，隔 3 s 两次采样 | **`0.0199` → `0.0199`（`Time.frameCount` 恒等于 2）** | **帧循环彻底冻住**——不是「没生成」，是「世界没在走」 |
| `EditorApplication.isPaused / isCompiling` | `False / False` | 不是暂停按钮，也不是在编译 |
| `Application.runInBackground` | **`False`** | ← 真凶 |
| 把 `runInBackground` 置 `true` 后立刻采样 | `frameCount` 2 → **4173**，`elapsed` 涨到 5.35 | 冻住与失焦**因果确认** |
| 复活英雄 + 手动驱动一枪（真实世界、真实 Job） | `kills=4`，`Enemies 1000 → 996` | **战斗链在真实世界里也是通的** |
| `CombatSmokeTest.RunAndReport()` | **PASS 9 / FAIL 0** | 项目自检同样证明链是通的 |
| 进战斗后采样英雄血 | `165 / 200`（约 3 秒接触） | 站原地被围约 **11 dps**、约 **20 秒**阵亡（100 血时实测是 11 秒，与 §5 旧记录一致） |

**结论：这一轮没有任何一行战斗代码是坏的。** 用户看到的是三种「什么都没有发生」叠在一起，而它们在画面上**完全一样**：

| # | 状态 | 画面表现 | 为什么会被误判成「伤害没实现」 |
|---|------|----------|--------------------------------|
| 1 | **Play 被暂停**（编辑器失焦） | 画面定格，武器仍叠在兵身上（因为兵停在 1.5 m 环上，而刀身 2.8 m 会压过去） | 「武器碰到小兵却不掉血」的字面观感，一字不差 |
| 2 | **英雄已阵亡** | 攻击链被 `HeroAttackSystem` 的 `HeroDead` 早退永久冻结，字灰化、结算面板出现 | 玩家手还在 J 上，按了没反应 ⇒ 「攻击坏了」 |
| 3 | **Game 视图没焦点** | `Input.GetKey(KeyCode.J)` 恒为 false，HUD 一直显示「未按」 | 与「输入层坏了」长得一样 |

第 1 条其实**早就被记录过**（`AGENTS.md` MCP 通道大坑 §1：编辑器不在前台时主循环几乎不走，并提到 `Application.runInBackground = true` 能解），但它一直被当成「查 bug 时临时开一下」的手段，**从来没有写进项目设置**。于是每一轮都重新踩一次：AI 在运行时把它打开、看到画面正常、报「已修好」；用户下次自己 Play，又回到默认的暂停态。

## 备选方案（Options）

| 方案 | 做法 | 判断 |
|------|------|------|
| A. 只在文档里再提醒一次「记得开场前设置 runInBackground」 | 继续靠人记 | ❌ 已经失败过一轮。这正是 ADR-0016 的同一课：**修复不许依赖人记得执行某个动作** |
| B. 加一个「运行态自检」按钮 | 让玩家/开发者点一下检查环境 | ⚠️ 治标。默认态仍然是坏的，而且又增加一个要记得点的动作 |
| C. **把 `runInBackground` 写进 `ProjectSettings`（持久）** + HUD 自证 + R 键重开 | 默认态正确，异常态可见可恢复 | ✅ 见下 |

---

## 决策（Decision）

**C：把三条前提分别落在「默认态 / 可见性 / 可恢复性」上。**

### 1. `PlayerSettings.runInBackground = true`（持久化，默认态正确）

写进 `ProjectSettings/ProjectSettings.asset`（`runInBackground: 1`），不是运行时临时设。

**为什么必须是项目设置而不是各自在代码里设**：运行时设只对「AI 正在操作的那一次 Play」有效。AI 一旦退出，用户自己按 Play 就又回到默认的暂停态——而**用户看到的就是那一次**。

代价：背包里游戏失焦不再自动暂停，编辑器里会持续吃 CPU。可在 `Window > MCP for Unity` 需要低占用时手动关掉，但默认要开。

### 2. HUD 把「键到底进没进来」摊在屏幕上

`HudController` 的 `突刺 J` 读数在「未按」分支补一句**「先点一下 Game 窗口再按」**。

理由：编辑器里 legacy `Input` 只送给**有焦点的 Game 视图**。玩家在 Scene 视图/Inspector 里按 J 时，HUD 会一直显示「未按」——它既不是输入层坏了也不是判定坏了，纯粹是焦点没给对。这句话把第三种「什么都没发生」变成一眼可辨的文字。

### 3. 阵亡必须能一键恢复

`HeroAttackSystem` 与 `EnemyAttackSystem` 都在 `HeroDead` 时早退（ADR-0014 的设计），所以**阵亡后整条攻击链是永久冻结的**。原本只给了一个「重开一局」按钮，而这个时刻玩家的手正在键盘上（J 键）。

新增 **R 键直接重开**（`HudController.Update`，仅 `_heroDead` 时生效；与移动 / 攻击 / 切视野都不冲突），结算面板同步补上「R 键重开一局」提示。

### 4. 记录「自检世界的裁剪」不是 bug

`CombatSmokeTest` 的世界故意只挂 8 个系统（不挂 `HeroMoveSystem` / `BoidsSystem`），于是 Entities 会丢掉 `EnemySpawnSystem` 的 `[UpdateBefore(HeroMoveSystem)]` 并每次排序打一条 `Ignoring invalid [UpdateBeforeAttribute]`——**跑一次刷 10 条，是正常的**。

不修的理由（试过）：补挂 `HeroMoveSystem` 只是把警告挪到它 → `BoidsSystem` 那条上；再补挂 `BoidsSystem` 又会用分离力把用例 3 里间距 0.4 m 的五个兵推开，等于改了被测语义。**噪音的正确归宿是写进注释与文档，不是硬压掉。**

## 后果（Consequences）

### 正面

- **默认态就是可观测态**：用户自己按 Play 之后，切到任何窗口游戏都继续跑。这一轮的误判从根上消失。
- 「按了没反应」有了**分诊顺序**：HUD 帧率/时间在动吗（暂停？）→ 攻击读数是不是「未按」（焦点？）→ 有没有结算面板（已阵亡？）。三条各有一眼可辨的特征，不再需要读代码反推。
- 阵亡后**一条键盘路径**回到可玩态，不必挪视线去找按钮。

### 负面 / 需要接受的代价

- 编辑器失焦时持续吃 CPU（1000 实体约数十 fps）。若将来字潮上到万级，需要重新权衡——那时更该做的是**帧率上限**而不是靠失焦暂停省电。
- R 键占用了。目前它没有被任何系统使用（移动是 WASD/方向键、攻击是 J/鼠标左键、视野是 Space、返回是 Esc）。将来加技能键时要回来复核。
- `runInBackground` 是**项目设置**，会进 git；跨平台构建（Steam）同理生效——这是想要的。

### 后续动作

- [ ] 若用户仍报「没反应」，按 ADR 里那张三列表**从上往下**问，不要再从代码查起
- [ ] 万级字潮性能实测时复核「常开 runInBackground 的 CPU 占用」是否有必要加帧率上限

---

## 复核条件（何时重新评估）

- **再出现一次「玩家说没反应，而代码全对」** → 说明这三条前提外还有第四条未知前提，必须补进本 ADR 的三列表
- **新增任何占用 `R` 键或改变「阵亡后能不能动」的设计** → 第 3 条要重新设计
- **字潮规模上到万级** → 第 1 条的 CPU 代价需要重新衡量
