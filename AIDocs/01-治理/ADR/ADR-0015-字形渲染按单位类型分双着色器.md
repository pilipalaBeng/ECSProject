# ADR-0015: 字形渲染按单位类型分双着色器，英雄状态表现收口在单个写入方

> **状态**：已采纳
> **日期**：2026-10-09
> **决策者**：扣丢桑（拍板「你来改吧」，需求为「体现英雄血量 / 兵受击变色 / 兵死即删 / 英雄血空即结束 / 英雄死亡变色」）
> **影响范围**：`Data/Shaders`（新增 `GlyphFlat.shader`）、`Editor`（`GlyphAssetBuilder`）、`Presentation`（`HeroWeaponView` / `HudController`）、`工程事实.md` §2/§5、`AGENTS.md` 踩坑录
> **关联 Spec**：无（属缺陷修复 + 表现层补全，见「背景」中的实测数据）

## 背景（Context）

用户报的现象是一组：**武器自己走自己的 / 英雄单位不会动 / 英雄掉没掉血不知道 / 小兵掉没掉血不知道 / 武器有没有伤害不知道**。同时提出五条表现需求：体现英雄血量、兵受击变色、兵血空即删、英雄血空即游戏结束、英雄死亡变色。

排查中有一个**看起来像 ECS 问题的现象**，实测出来却是渲染问题。取证过程与数据（全部来自工程文件与截图，未依赖运行时探活）：

| 证据 | 内容 |
|------|------|
| 代码 | `HeroWeaponView.PlaceWeapon` 把武器落在 `heroPos + forward × 距离`，距离 ∈ `[0.55, 2.4]`。**武器在 XZ 上不可能离英雄超过 2.6 米** |
| 配置 | `Mat_Weapon._Color = (0.88, 0.84, 0.62)`；截图中那根亮条实测 `(224, 214, 158)`，逐分量精确命中（Gamma 空间），长度 33 px × 2 px ↔ 1.8 m × 0.12 m，两个维度自洽 → **标定 18.33 px/m** |
| 截图 | 金色块（英雄材质色族）实测 15×15 px ↔ 1.1 m × 1.1 m；亮条（武器）与金色块相距 133.8 px ↔ **7.3 米**。亮条周围有一圈兵字空地 = `StopRadius`（1.5 m）的内侧空洞 → **亮条所在处才是英雄真身** |
| 材质 | `Mat_Glyph_Hero.mat` 的 `m_Shader` guid = `63c1aada…` = **`GlyphInstanced.shader`** |
| 着色器 | `GlyphInstanced.vert` 全程只有 `mul(UNITY_MATRIX_VP, float4(world, 1))`，`world` 来自 `_GlyphInstances[SV_InstanceID]`，**没有任何一处读 `UNITY_MATRIX_M`** |
| 绑定方 | `_GlyphInstances` 只被 `InstancedEnemyRenderer` 绑在**敌人材质**上（`Mat_Glyph_Bing`）。英雄是个普通 `MeshRenderer`：`SV_InstanceID` 恒为 0，材质上又没绑过缓冲 → 读到零 |
| 相机 | 正交 18 → 659 px 高窗口 = 18.33 px/m，与武器标定自洽；金色块在裁剪图里的位置与「真身在 (−7.0, +1.9)、字形被钉在原点」完全吻合 |

**结论**：英雄字块被画死在**世界原点**、尺寸恒为 `_GlyphSize`（1.1 米，与一个「兵」字等大），与它自己的 `Transform` 毫无关系；而武器材质是 `Unlit/Color`（读 Transform），老老实实跟着真身跑。玩家看到的「英雄不动、武器自己走自己的」是**同一个根因**的两面。相机跟随、武器落位、输入链、伤害链、兵死亡销毁全部正常——`CombatSmokeTest` 8 项断言本就全 PASS，问题纯粹在「英雄在哪」没有被画出来。

同时暴露三条**表现层的空白**（不是 bug，是没做）：英雄血量只有文字、没有形状；英雄阵亡只有一行小字；英雄阵亡没有任何视觉变化。

## 备选方案（Options）

### 字形渲染：怎么让英雄认 Transform

| 方案 | 做法 | 判断 |
|------|------|------|
| A. 给 `GlyphInstanced` 加「没有实例缓冲时回退到 Transform」分支 | 一个 shader 两套语义，靠运行时状态（缓冲是否绑定）决定走哪条 | ❌ 分支判据在 GPU 侧不可靠；direct/indirect 两种绘制的实例序号语义不同；一个着色器里塞两套顶点变换，以后每次改动都要同时验证两条路 |
| B. 新增 `GlyphFlat.shader`，由材质决定语义 | 英雄走 `UnityObjectToClipPos`，字潮继续走 indirect | ✅ 边界落在**材质资产**上，一眼可见、Inspector 可查；两个 shader 各自只有一条路，改动互不影响 |
| C. 英雄也改用 `DrawMeshInstancedIndirect`（1 个实例） | 复用现成 shader | ❌ 为了复用着色器引入一整条 args/ComputeBuffer 通道来画一个字；且英雄尺寸来自 GameObject scale（它是两个字的宽度），走实例缓冲反而要把 scale 折进 `_GlyphSize` |

### 英雄状态着色：写在几个 MonoBehaviours 里

| 方案 | 做法 | 判断 |
|------|------|------|
| A. 新开 `HeroDamageView`，与 `HeroWeaponView` 各写一份 MPB | 职责看起来更纯 | ❌ `MaterialPropertyBlock` 是挂在 Renderer 上的共享状态，两个写入方互相覆盖，结果随脚本执行顺序变——表现成「闪红时有时无」这种最难查的偶发 |
| B. 扩 `HeroWeaponView`，颜色通道收成一个写入方 | 底色与受击层分成两个通道（`_Color` / `_Flash`） | ✅ 一个写入方是硬保证；受击与阵亡是同一件事（伤害状态）的两个表现，本就在同一职责下 |
| C. 阵亡改材质实例（`renderer.material`） | 换一个灰色材质 | ❌ 会生成材质实例、污染资产，且与既有的 MPB 通道并存 |

### 阵亡判据来源

| 方案 | 判断 |
|------|------|
| 表现层自己判 `Health.Value <= 0` | ❌ 会把「未初始化（`Max = 0`）」也算成死亡（开局第一帧整块字变灰）；且与 `ApplyDamageSystem` 的判据形成**两份真相**，迟早漂移 |
| 读 `BattleProgress.HeroDead` | ✅ 唯一来源，由 `CommitBattleProgressJob` 写；表现层只读一个 bool |

## 决策（Decision）

**着色器分家（B）+ 颜色单写入方（B）+ 判据读 `HeroDead`。**

### 1. 新增 `HanziRogue/GlyphFlat`，两种单位两种着色器

| 单位 | 着色器 | 位置来源 | 尺寸来源 | 闪色通道 |
|------|--------|---------|---------|---------|
| 字潮（兵） | `GlyphInstanced` | `StructuredBuffer<GlyphInstance>`（`SV_InstanceID` 索引） | `_GlyphSize`（统一 1.1 m） | 缓冲里的 `Flash` 标量 |
| 英雄等单实例单位 | `GlyphFlat` | `UNITY_MATRIX_M`（`UnityObjectToClipPos`） | GameObject 的 `localScale` | MPB 的 `_Flash` |

两个 shader 的属性表**刻意对齐**（`GlyphFlat` 多一个 `_Flash`、少一个 `_GlyphSize`），这样两种字形在 Inspector 上长得一样，表现层换着色器不用改 C#。两者都必须 `Cull Off`（俯视看的是 quad 背面）。

**着色器选型收口在 `Editor/GlyphAssetBuilder.EnsureMaterial`**，由 `instancing` 布尔决定，不由调用方各写一份 shader 名——两边共用同一个着色器正是这次的根因，把选型收在一个分支里，下次改不动它。

同时 `EnsureMaterial` **无条件重写** `material.shader`：这正是「重跑一次字形装配即可修好英雄字块」能成立的原因（不需要手改资产）。

### 2. 英雄外观的唯一写入方是 `HeroWeaponView`

- `_Color`：底色通道 —— 常态取 `sharedMaterial.color`（金橙），阵亡按 `deathColor` 灰化；
- `_Flash` + `_FlashColor`：受击通道 —— 强弱由 `HitFlash.Timer / HitFlashDuration` 给。

分成两条通道而不是在 C# 里合成一个颜色：合成会让「正在闪红的时候被打死」这种**叠加态**没有确定结果，而那恰好是最常见的死法。

阵亡灰化用 `Mathf.MoveTowards` 缓动（`deathFadeTime = 0.5s`），不用 `Lerp(…, 常数)`——后者的收敛速度会随帧率变。阵亡时武器回到 `restDistance`：相位已被冻结，不收回去枪会停在「半空」那个姿态上，看起来像卡死。

### 3. `HeroDead` 是唯一的阵亡判据

`HudController` 与 `HeroWeaponView` 都只读 `BattleProgress.HeroDead`，谁也不自己比血量。理由与 `CombatRules.IsInitialized` 同源：同一判据写两处必然漂移，且漂移出来的是静默 bug。

### 4. HUD 加形状，不只是数字

- 英雄血条：满血金橙（与英雄字同色，一眼对得上是「我」）→ 残血朱砂，**颜色本身就是刻度**；
- `剩余兵 N / 总数`：分母让它成为整场战斗唯一的进度条；
- 阵亡时压暗全屏 + 居中「游戏结束」面板 + 「重开一局」。

「重开一局」走 `ModeSwitcher.EnterBattle`，**不新开重置入口**：它会调到 `BattleSession.Enter`，而后者先清场再建局，所以「重开」与「首次进战斗」本来就是同一条路径。

## 后果（Consequences）

### 正面

- **英雄终于可见**：字块回到该有的 3.0 × 1.5 米、跟着 ECS 位置走；武器与它重新合成一件东西。
- **表现层颜色有了硬边界**：一个写入方，不会出现「闪红时有时无」这类与脚本顺序耦合的偶发。
- **阵亡第一次有画面**：灰化 + 结算面板，玩家不会再把「英雄变灰」当成渲染故障。
- **修法可复现、不需要手改资产**：重跑 `HanziRogue/Build Minimal Scenes`（或 `Rebuild Glyph Assets`）即自动把 `Mat_Glyph_Hero.mat` 的 shader 纠回来。
- **错误被写进错题本**：`AGENTS.md` 新增三行（共用 instancing 着色器 / MPB 两个写入方 / 表现层自判血量）。

### 负面 / 需要接受的代价

- **两个 shader 属性表要靠人保持对齐**。目前是注释约束（`GlyphFlat.shader` 顶部写明分工），编译器不管。
- **英雄的尺寸语义从 `_GlyphSize` 改成 `localScale`**，与字潮不再一致。这是必要的：英雄是两个字的宽度（3.0 × 1.5 m），而字潮是统一的正方形。
- **`HeroWeaponView` 的职责扩张了**：从「枪的动画」扩到「英雄的全部外观着色」。名字不再精确（叫 `HeroWeaponView` 却管着英雄字色）。改名会动到场景里的 MonoBehaviour 引用，风险大于收益，故保留名字并在类注释里写明。
- **HUD 仍是 IMGUI**。加血条后它的职责从「读数」扩到「状态呈现」，将来引入 UGUI 时整块要重写。

### 后续动作

## 复核条件（何时重新评估）

- **出现第二个单实例字形单位**（精英兵 / BOSS / 拾取物）→ 复核 `GlyphFlat` 是否够用，尤其是「序列帧 UV 偏移」是否需要走 per-instance 通道
- **英雄需要序列帧动画**（受击帧 / 死亡碎裂纹理）→ `GlyphFlat` 的 `_MainTex` 采样要加 UV 偏移，那时评估是否回到 instanced 路线
- **引入 UGUI / TextMeshPro 做 HUD** → 本 ADR §4 整块重写
- **`HeroWeaponView` 需要再加第三类表现**（比如拾取物挂载点）→ 职责已过载，拆分时机到了（拆分时要先把 MPB 写入方收敛成一个，再考虑拆组件）
- **需要真正测性能** → 本 ADR 未提供 ms 基线；字潮路径未改动，但英雄从 instanced 改为普通 MeshRenderer 多了一个 draw call（1 个），需在 Profiler 里确认可忽略
