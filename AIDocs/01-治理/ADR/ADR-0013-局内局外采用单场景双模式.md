# ADR-0013: 局内局外采用单场景双模式，一局边界归 BattleSession

> **状态**：已实施并实测回填（2026-10-07）
> **日期**：2026-10-07
> **决策者**：扣丢桑（问「局内局外两个场景好还是一个场景好」「主流项目也是建议同一个场景内做局内局外呗」）+ AI（诊断、核实与实施）
> **影响范围**：新增 `Core/GameMode`、`Presentation/ModeSwitcher`；`Presentation/BattleBootstrap` 改名 `BattleSession`（`git mv`，脚本 guid 不变）；改 `MetaController` / `HudController` / `SceneNames` / `SceneBuilder` / `Editor/SceneFlowSmokeTest`；场景 `MetaScene` + `BattleScene` → `MainScene`；文档 `工程事实.md` / `AGENTS.md` / `无头验证通道.md` / `系统地图.md`
> **附带修复**：`Presentation/InstancedEnemyRenderer` 分批回读的等长约束 bug（本轮 Play 模式实测才发现，见「附带发现」）

## 背景（Context）

### 原状

两个单载场景（`MetaScene` 局外 / `BattleScene` 局内），切换走 `SceneManager.LoadScene(Single)`。
两个场景都只有 GameObject 层内容，ECS 实体全部由**运行时代码** `CreateEntity` 产生。

### 实测一：局内局外并不独立，往返会崩

前序排查（`Editor/SceneFlowSmokeTest`，同一 World 上跑两次真实 `BattleBootstrap.Start()`）实测：

| 观测点 | 不清场直接二次进战斗 | 进战斗前清场 |
|---|---|---|
| 二次进战斗 `GameConfig` 数 | **2** | 1 |
| 之后 20 帧系统异常 | **40 条** `InvalidOperationException` | **0 条** |
| 英雄位移 | **0.000 m** | 4.667 m（= 14 m/s × 1/3 s） |
| 兵平均位移 | **0.000 m** | 4.066 m |

40 = 20 帧 × 2 个系统（`HeroMoveSystem` + `BoidsSystem`）。`EnemySpawnSystem` 因为先查
`EnemyTag` 数量就 `return`，侥幸没炸。

症状**不是崩溃**，是每帧刷屏 + 字潮和英雄**全部定格**：`GetSingleton<GameConfig>()` 在
「恰好 1 个实体」不成立时抛异常，异常被 `ComponentSystemGroup` 捕获后打日志、跳到下一个系统。

根因在 Entities 1.0.16 源码里写得很清楚：

- `DefaultWorldInitialization.cs:46` —— 默认 World 建在
  `RuntimeInitializeOnLoadMethod(SubsystemRegistration)`，那是「进入 Play 会话」的时机，
  **不是加载场景的时机**。`SceneManager.LoadScene` 不动它。
- `RuntimeContentManager.cs:205` 是唯一订阅 `SceneManager.sceneUnloaded` 的地方，
  只释放 subscene/blob 内容，**不销毁运行时 `CreateEntity` 建的实体**。

### 实测二：局外期间 ECS 照跑

World 挂在 PlayerLoop 上，只有域卸载 / 切换播放模式才摘除。局外停 60 帧，兵到英雄的平均距离
仍在变——系统确实还在推进。10 万实体时这就是纯白烧 CPU。

### 核实：两种「主流」是相反的

追问「主流项目也这么做吗」时核实过一手资料，结论必须分两种主流说，否则会误导：

- **传统 Unity（GameObject 项目）主流 = 分场景**。MenuScene / GameScene / ResultScene +
  `LoadScene(Single)`，Unity 官方教程就是这么教的。前提是游戏状态活在 GameObject / MonoBehaviour
  层：卸载场景 = 状态清空，边界自洽。
- **DOTS 主流 = 一个常驻主场景 + SubScene**。这是官方立场，SubScene 文档原话：
  「实体组件系统 (ECS) 使用子场景而不是场景来管理应用程序的内容。这是因为
  **Unity 的核心场景系统与 ECS 不兼容**。」
  官方 DOTS roundtable 中被问到「文档说 ECS 与多场景架构不兼容，该怎么做」时，Joe Valenzuela 的
  答复是：ECS 不禁止 additive 加载多个 Unity 场景，**但那些场景里不会有任何 ECS 数据，只有
  GameObject 和 MonoBehaviour**；ECS 数据要作者化进 SubScene 再烘焙。

**现状两头不靠**：用传统主流的写法（两个普通 Scene）去装 ECS 内容，
既拿不到「卸载即清状态」（状态在常驻 World 里，不归场景管），
也拿不到「实体与场景绑定的生命周期」（没用 SubScene，实体不归任何场景）。

## 备选方案（Options）

| 方案 | 优点 | 缺点 | 判定 |
|------|------|------|------|
| A. 保持两场景，只在 `BattleBootstrap` 里补清场 | 改动最小，直接消灭 40 条异常 | 清场逻辑一样要写；已付两个场景的全部成本，只买到「表现层自动拆装」半份收益；场景边界与状态边界**永久错开**，后来者每次都要重新理解一遍 | ❌ 治标 |
| **B. 单场景 + 双模式（两组根节点 `SetActive`）** | 表现层仍然整体拆装；切换成本从「加载场景」降到「切激活」；模式与 ECS 状态一一对应，边界自洽 | 场景树变复杂（三组根节点）；相机要两台；需显式管理根节点激活 | ✅ **选定** |
| C. 主场景 + SubScene | DOTS 原生流式，实体生命周期真正绑定内容 | 现阶段引入烘焙管线 / 增量烘焙 / 异步流式的复杂度，而项目还没有可拆分的内容；等于用未来问题换现在问题 | ❌ 过度设计 |
| D. 每局新建 / 销毁 World | 「一局」边界最物理 | 系统创建、Burst 编译缓存、增量 TypeManager 全部要跟着重建，成本远超收益 | ❌ 不值当 |

---

## 决策（Decision）

**选方案 B。** 判据一句话：

> **一个场景 = 一个 ECS World 的生命周期。**

局内局外共用同一个常驻 World，所以它俩本质上是**同一个场景的两种模式**。用两个普通 Scene 去表示
它们，等于拿一把量不了 ECS 的尺子去量 ECS 状态——前序实测那个坑就是这处错配的产物，
不是「忘了清场」。

### 1. 目标结构

```
MainScene.unity
├── GameFlow                      常驻，不随模式切换
│   ├── AudioListener             全局唯一（两个 root 互斥，不能各挂一个）
│   ├── ModeSwitcher              切 MetaRoot / BattleRoot 显隐
│   └── BattleSession             ScaleConfig → ECS 的唯一桥接点
├── MetaRoot                      局外模式
│   ├── MetaCamera                Camera (MainCamera)
│   └── MetaUI                    MetaController
└── BattleRoot                    局内模式（默认失活）
    ├── BattleCamera              Camera (MainCamera) + BattleCamera
    ├── Ground / EnemyRenderer / Hero / HUD
```

两台相机都打 `MainCamera` 标签：两组根节点互斥，任一时刻只有一台激活，所以 `Camera.main`
在两种模式下都指向当前那台。共用一台则要在局外模式里关掉跟随逻辑，多写分支还容易让
`Camera.main` 指到战场相机。

### 2. `BattleSession` 是工程里唯一写明「一局边界」的地方

`BattleBootstrap` 用 `git mv` 改名而来（保脚本 guid，不新建再删），职责从「写一次 GameConfig」
扩成「一局的开与关」：

- `Enter()` = 清场 → 建 `GameConfig` singleton
- `Exit()` = 清场
- 私有 `Purge(World)` = 销毁 `GameConfig` / `HeroTag` / `EnemyTag` 三类实体

**`Enter` 自己做清场，而不是指望调用方先调 `Exit`**：重进、重开、异常恢复都走同一个入口，
少一个「忘了先退出」的失败模式。

英雄实体一并删掉——它由 `EnemySpawnSystem.SpawnHero` 在清场后重新生成；只删兵的话，
上一局的英雄会留在原地，再进战斗时 `HeroView` / `BattleCamera` 直接跟过去、画面跳一下。

### 3. `ModeSwitcher` 只管模式，不碰 ECS

`[SerializeField] metaRoot / battleRoot / session`；`EnterBattle()` / `EnterMeta()` 只做
「切 `SetActive` + 调 session」。职责单一，不碰相机参数、不碰 ECS。

`MetaController` / `HudController` 的 `LoadScene` 换成模式切换——这两个类此后不再依赖
`UnityEngine.SceneManagement`。

### 4. 旧的两个场景文件保留在磁盘

只是退出 Build Settings、`SceneBuilder` 不再生成它们。删文件要单独决策，不顺手删。

## 后果（Consequences）

### 正面

- 往返不再定格：二次进战斗 `GameConfig` 恒为 1，系统零异常（见「实测回填」）
- 局外不再白烧 CPU：`Exit()` 把实体清空，系统空转（实测局外 `configs=0 heroes=0 enemies=0`）
- 模式与状态一一对应：`GameMode` 是个枚举，不再是「当前在哪个场景」这种要靠推断的东西
- 切换成本从「加载场景」降到「切激活」，且表现层依然整体拆装（`SetActive` 会停掉整棵子树的
  `Update`，`BattleCamera` / `HeroView` / `HudController` 不用各自判「我现在该不该跑」）
- 场景装配仍是 `SceneBuilder` 一键生成，不依赖人工点编辑器

### 负面 / 需要接受的代价

- **相机两台**：`MetaCamera` 与 `BattleCamera` 各自成树，配置重复一份。换来的是不必在局外模式里
  分支关掉跟随逻辑
- **场景树变深**：三组根节点的激活状态成了新的「隐性契约」。缓解办法是 `ModeSwitcher.Current`
  作为唯一可读的模式来源，不许别处猜根节点激活状态
- **`Awake` 里做了一次 `Exit()`**：场景装载时以局外为准。编辑模式下 `AddComponent` 不触发
  `Awake`，所以自检里的起点由字段默认值决定、而非 `Awake` 决定——这层差异靠 Play 模式实测补上
  （见「实测回填」）
- **`EnemySpawnSystem` 的生成判据仍是「是否已存在 `EnemyTag`」**：清场把它删干净，所以往返能正确
  重新生成；但将来做「清场玩法」（兵被杀光）时，它会**再生成一整套**。本次不动（改动范围最小化），
  写进复核条件

### 本轮不做

- `BattleScene.unity` / `MetaScene.unity` 的文件删除（保留在磁盘，只是退役）
- `EnemySpawnSystem` 生成判据的改造（属「清场玩法」的独立设计决策）
- SubScene 迁移（见复核条件）

## 附带发现：`InstancedEnemyRenderer` 分批回读的等长约束 bug（本轮修复）

**不属于本 ADR 的决策范围，但由本轮 Play 模式实测才暴露，一并记录。**

工作区里未提交的 ADR-0011 并行化改动把主线程逐元素赋值循环换成了：

```csharp
_nativeMatrices.GetSubArray(offset, count).CopyTo(_batchBuffer);   // ❌
```

`NativeArray<T>.CopyTo(T[])` 要求源与目标**等长**，而 `_batchBuffer` 恒为 `BatchCap`（1023）。
于是只要 `count != 1023`（本例 1000 实体，单批不满）就抛：

```
ArgumentException: source and destination length must be the same
  Unity.Collections.NativeArray`1[T].CheckCopyLengths(...)
  ...InstancedEnemyRenderer.Update ()  (at InstancedEnemyRenderer.cs:103)
```

症状恶劣：**异常先于 `DrawMeshInstanced` 抛出**，字潮一个都不画，而且每帧刷屏。

HEAD 版本用的是逐元素赋值循环（`_matrices[i] = ...`），没有等长约束——所以这是
**并行化改动引入的新缺陷，不是存量问题**。

修法（1 行，走部分拷贝重载）：

```csharp
NativeArray<Matrix4x4>.Copy(_nativeMatrices, offset, _batchBuffer, 0, count);   // ✅
```

修复后复跑 Play 模式：字潮 `LastRenderedCount=1000`，Console **0 条 error**。

> **教训**：`NativeArray<T>.CopyTo(T[])` 与 `GetSubArray(...).CopyTo(...)` 看着等价，实际前者要求等长。
> 这类错误在**无头自检里看不见**（自检不跑渲染器），只有真实进入 Play 才会暴露——
> 又一次验证了「表现层行为必须实跑取证」。

## 复核条件（何时重新评估）

- **局外长成有自己重内容的模块**（构筑 / 图鉴 / 编队 / 独立 3D 展示），且需要独立加载进度时
  —— 按「**一场景一 World**」重新拆分；判据参考：局外单模块内容量超过局内的 **1/3**
- **需要按关卡拆分战场内容、或需要流式加载时** —— 走 DOTS 正解：`Boot 常驻场景 + SubScene`
  （而不是再加一个普通 Scene）；Additive 加载可以继续留给纯 UI
- **做「清场玩法」（兵被杀光）时** —— `EnemySpawnSystem` 的「是否已存在 `EnemyTag`」生成判据会
  再生成一整套，必须先改造
- **表现层出现「按模式分支」的需求时** —— 读 `ModeSwitcher.Current`，不要读根节点的
  `activeSelf`；若发现两处以上在猜激活状态，说明该契约需要显式化

### 验证通道备忘（本轮补充）

沿用 ADR-0011 的两条结论，并新增三条：

1. **MCP 通道读不到 `LogType.Log`**（`types:["log"]` 返回 0 条）→ 结论必须走**返回值或落盘文件**。
   本轮自检落盘 `Logs/sceneflow_report.txt`。
2. 排查需要准确托管堆栈时注掉 `[BurstCompile]`，定位完恢复。
3. **新增**：`execute_code` 长调用会掉 WebSocket 连接（`success:false, message:null`）。
   对策：`EditorApplication.delayCall += delegate(){...}` 挂延迟回调后立即返回，再用轻量调用推帧。
4. **新增**：**编辑模式下 `AddComponent` 不触发 `Awake`**。所以自检里的组件起点由字段默认值决定；
   `Awake` 的行为只能靠真实 Play 模式验。
5. **新增**：MCP `execute_code` 对含 `EditorApplication.Exit` 字样的代码有安全拦截
   （`ExitPlaymode` 会被误伤），需要 `safety_checks=false` 放行。
