# ADR-0014: 战斗闭环走单一伤害写入点，渲染通道升级为 indirect

> **状态**：已采纳
> **日期**：2026-10-07
> **决策者**：扣丢桑（拍板「渲染走 indirect」「P1~P4 一次做完」）
> **影响范围**：`Core`（Combat / GameState / CombatConfig / CombatBalance）、`Gameplay`（六个新 System + 生成判据）、`Presentation`（indirect 渲染 / HeroWeaponView / HUD / BattleSession）、`Editor`（SceneBuilder / CombatSmokeTest）、`数值预算表.md` §5、`工程事实.md` §2/§5、`AGENTS.md` 踩坑录

---

## 背景（Context）

最小闭环（千兵追英雄）已经能跑：1000 个「兵」字从外环扑向英雄、贴住、字间距 1.08 m。**但它没有任何伤害概念**——英雄和兵都只是一堆带 `Position2D` 的实体，谁打谁、谁掉血都还没有宿主。

本次要加的是最基础的一层：英雄能突刺、兵有血、受击有反馈、会死、英雄也会死。约束来自三条：

1. **以后还要往里加东西**。宪法 §2.5 已经写明五行相克是唯一伤害规则（倍率 1.0 / 3.0 / 0.4），C4.5 已经写明死亡要 6 帧碎裂序列帧。所以这次不能只求「能扣血」，得把**相克倍率和序列帧将来要接进来的口子留对**。
2. **代码不能写得暴躁**。用户原话：「不能为了简单实现就写得很粗糙，注意代码耦合」。
3. **数字必须实测**（宪法 §4.3）。这次新增了 12 个手感数值，一个都不许凭观感下结论。

三个具体的技术问题必须当场定，它们都有返工风险：

| 问题 | 走错路的代价 |
|------|--------------|
| 命中判定复用 `SpatialGrid` 吗 | 把格网提成跨 System 共享要付生命周期与排序依赖的代价，而收益接近零 |
| 受击染色走哪条渲染通道 | 选错了，做碎裂序列帧时要整套重做 |
| 伤害怎么从攻击方传到血量 | 留了第二个 `Health` 写入点，将来每个跨系统效果都要在每处重实现一遍 |

---

## 备选方案（Options）

### 命中判定

| 方案 | 优点 | 缺点 | 成本 |
|------|------|------|------|
| A. 复用 `SpatialGrid` 做 3×3 邻域查询 | 与 BoidsSystem 走同一条路，「看起来统一」 | 格网要提成跨 System 共享状态：谁建谁销毁、System 排序依赖、每帧搬运 struct。而攻击判定是**单中心查询**，本来就不是邻域配对 | 中 |
| B. 每次攻击做一次 O(n) 距离判定 | 零共享状态、零排序依赖、实现直白 | 规模上去后单次成本线性增长 | 低 |

### 受击染色通道

| 方案 | 做法 | 判断 |
|------|------|------|
| A. 双批次 `DrawMeshInstanced` + `MaterialPropertyBlock` | 正常一批、闪白一批 | ❌ MPB 只能给**整批**统一赋值。同一帧受伤的兵共用一条淡出曲线，不同时刻受伤的会同步跳变；且这条路在做序列帧时注定重做 |
| B. `DrawMeshInstancedIndirect` + `StructuredBuffer` | 每实例数据进 ComputeBuffer，shader 按 `SV_InstanceID` 索引 | ✅ 顺带消掉 C4.3 的 1023 分批限制 |
| C. 引入 `com.unity.entities.graphics` | 走 DOTS instancing | ❌ 包未装，Built-in 管线 + Entities 1.0 的接入成本高，收益与 B 相同 |

### 伤害传递（**实施中修正，与 Spec 不同**）

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. `NativeQueue<DamageEvent>` 事件队列（Spec 原案） | 教科书解法，陌生读者一眼认得 | 跨 System 共享队列要额外管生命周期（谁建谁销毁）与依赖排序；队列条目还要带 `SourceKind` 等元数据 |
| B. `PendingDamage` 每实体累加器（**实际采用**） | 无共享状态、无队列生命周期、无排序依赖；写入方天然唯一 | 隐含「同一目标集只有一个伤害源」的不变式，必须写死在组件注释里 |

---

## 决策（Decision）

**命中判定选 B（O(n)），渲染通道选 B（indirect），伤害传递选 B（累加器）。**

### 1. 命中判定走 O(n) 单中心查询，不动 `SpatialGrid`

以英雄为单中心的查询复杂度是 `O(n·1)` 而不是 `O(n²)`，不违反 C1.8。1000 个敌人在 Burst job 里做一次投影判断是微秒级，而攻击平均每 0.35 秒才触发一次。

**这条是本方案里最想强调的「不要过度工程」判断**：把格网提成共享状态换来的收益接近零，代价却是真实的复杂度。

> **切换门槛（现在就写死，将来不要重开讨论）**：`EnemyCount > 5000` **或** 每秒攻击次数 > 10 次时，改为在 `SpatialGrid` 上做 3×3 单点查询。

### 2. 渲染升级 `DrawMeshInstancedIndirect` + `StructuredBuffer`

**选它的真正理由不是闪白**——闪白只是第一个用上 per-instance 通道的功能。C4.5 的死亡碎裂序列帧和 C4.2 的 sprite sheet UV 动画都需要同一条通道（每实例 UV 偏移），B 是唯一一条能一路走下去的路。闪白是顺带，1023 分批限制消失也是顺带。

### 3. `ApplyDamageSystem` 是全工程唯一的 `Health` 写入点，伤害用每实体累加器传递

```
生产者（只算「谁该掉血、掉多少」，不碰 Health）
    HeroAttackSystem   → 写兵的 PendingDamage.Amount
    EnemyAttackSystem  → 写英雄的 PendingDamage.Amount
消费者（唯一写 Health 的地方）
    ApplyDamageSystem  → 扣血 / 写 HitFlash / 判死 / 累加击杀
```

**为什么不用 Spec 里原定的 `NativeQueue<DamageEvent>`**：实施时发现伤害源的目标集**天然不相交**——英雄攻击只写兵的累加器，兵攻击只写英雄的累加器。每个实体的累加器全局只有一个写入方，于是既不需要原子操作，也不需要队列。

跨 System 共享 `NativeQueue` 要付出的是生命周期管理（谁建谁销毁）与依赖排序（谁先跑），换来的只是「形式上是事件」这一点观感。**这是有意的简化，不是偷懒**：省下来的是真实复杂度，而不是把复杂度藏起来。

**但代价必须写清楚**：累加器隐含「同一目标集只有一个伤害源」这条不变式。若将来出现第三个伤害源（比如环境伤害、反伤）写同一个实体，必须先回来改这条不变式——那时候说明该上真正的事件总线了，而不是就地绕过。这条不变式写在 `Combat.cs` 的 `PendingDamage` 注释里。

### 4. 附带决策（实施中才发现，一并记录）

| 决策 | 原因 |
|------|------|
| `CombatInitSystem` 必须 `[UpdateAfter(typeof(EnemySpawnSystem))]` | 只写 `[UpdateBefore(扣血系统)]` 不够。生成系统可能排在初始化之后，于是「实体刚建出来、血量还是 0」的那一帧照样会被结算系统看到 |
| 「未初始化」判据收敛成 `CombatRules.IsInitialized`（`Max ≤ 0`），三处必须一致使用 | 初始化 / 伤害结算 / 死亡判定漏任何一处，都会让开局第一帧的血量 0 被判成死亡，`HeroDead` 当场置位、整条战斗链永久冻结。表现出来是「攻击功能没实现」，排查方向会完全跑偏 |
| 英雄阵亡**不销毁实体** | 销毁会让全场所有依赖 `HeroTag` 的查询（移动 / 朝向 / 攻击 / 表现层多个读取）在同一帧集体落空，相机跟随对象直接消失。留一个血量为 0 的英雄实体比留一堆空引用判断便宜得多 |
| `Health.Value` 用 `float` 而非 `int` | 相克倍率 1.0 / 3.0 / 0.4 一接入伤害必然是小数。用 int 就得在接相克那天改组件类型，那是波及全部引用的破坏性改动 |

## 后果（Consequences）

### 正面

- **相克倍率有了唯一接入点**：将来实现 §2.5 的相克，只需在 `ApplyDamageSystem` 里乘一次倍率，不需要在每个伤害源里各改一遍。吸血、反伤、护盾同理。
- **per-instance 数据通道打通**：闪白已跑通，C4.5 的碎裂序列帧与 C4.2 的 UV 动画直接接这条通道即可，不必再动渲染架构。
- **1023 实例分批限制消失**：`DrawMeshInstancedIndirect` 的实例数由 args 缓冲给，没有硬上限。
- **战斗链可无头验证**：`CombatSmokeTest` 八条断言全 PASS，覆盖了「一刀结算两次」「杀光即重刷」这类只在特定时刻出现的 bug。
- **数值全部实测**：12 个新数值一个不剩地进了 `数值预算表.md` §5。

### 负面 / 需要接受的代价

- **渲染侧多了一层 CPU 回读**：每帧要把 `Position2D` / `HitFlash` 读成 `NativeArray` 再填进 ComputeBuffer，这批回读在有 `DrawMeshInstanced` 时也需要（只是形式不同）。
- **累加器的不变式是口头的**：编译器不会拦住第二个伤害源写同一个实体。目前靠注释与 ADR 约束。
- **Burst 内部编译错误**：`BuildGlyphInstancesJob` 触发 Burst 1.8.x 的 `Could not find type ... in assembly Burst.Compiler.IL.AssemblyNameReferenceAndMetadata`。这是 Burst 自身解析程序集引用表的故障，不是本工程的代码错误——摘掉该 job 的 `[BurstCompile]` 只会让控制台少一条 error，job 照样退回托管执行、性能并不会变好。**当前状态：已知问题，不影响正确性**，等 Burst 版本更新后自动受益。

### 后续动作

- [ ] 五行相克接入时，回到 `ApplyDamageSystem` 乘倍率（这是本 ADR 的主要目的）
- [ ] 做死亡碎裂序列帧时，走本 ADR 打通的那条 per-instance 通道
- [ ] 出现第三个伤害源时，重新评估「累加器 vs 真事件总线」
- [ ] Burst 包升级后复查 `BuildGlyphInstancesJob` 的编译错误是否消失

## 复核条件（何时重新评估）

出现以下任一情况时，应重新审视本决策：

- **`EnemyCount > 5000` 或 每秒攻击次数 > 10** → 命中判定切到 `SpatialGrid` 3×3 单点查询（这是写死的门槛，不是「感觉慢了再说」）
- **出现第二个写同一目标集 `PendingDamage` 的系统** → 累加器模型失效，改真事件总线
- **要接入 `com.unity.entities.graphics`** → 渲染通道可能整体迁移
- **需要「精锐兵伤害不同」** → `EnemyAttackSystem` 当前用「计数 × 伤害」折算（隐含所有兵伤害相同），需改成多计数槽或独立系统
- **Burst 包大版本升级后 `BuildGlyphInstancesJob` 仍报同样的错** → 不再是上游问题，回头查本工程
