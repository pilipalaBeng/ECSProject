# ADR-0006: 字形走离线位图烘焙 + 单字贴图实例化渲染

> **状态**：已采纳
> **日期**：2026-10-07
> **决策者**：扣丢桑（AI 提供分析与建议）
> **影响范围**：渲染管线、字形资产形态、CONSTRAINTS C2.3 / C3.3 / C4.1 / C4.2
> **关联**：ADR-0003（程序化序列帧美术）的**前置实现**——只做了「静态单字」，尚未做序列帧

---

## 背景（Context）

最小闭环要验证的画面是：**一千个「兵」字追着一个「英雄」两个字组成的单位跑**。
这就需要把汉字真正画到屏幕上。

硬约束横在面前：

- **C4.1**：禁止用 TextMeshPro 渲染战场实体（TMP 逐字渲染在万级必然崩）
- **C4.2**：字潮必须走 GPU instancing + sprite sheet
- **C2.6**：图集必须 Editor 阶段预烘焙，运行时动态生成会卡主线程

再叠加一个工程现实：本项目的验证通道是**批处理（`-batchmode -nographics`）**（见 `02-知识库/无头验证通道.md`）。
无图形模式下的字体光栅化不可靠。

---

## 备选方案（Options）

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 运行时 TMP 逐字渲染 | 一行代码就能显示 | **直接违反 C4.1**；千级必崩 |
| B. Unity Editor 脚本调 `Font.RequestCharactersInTexture` 烘焙图集 | 全程在 Unity 内，资产管线闭环 | batchmode `-nographics` 下动态字体图集不可靠；依赖 TMP 资产导入状态 |
| C. **Python(Pillow) 离线烘焙 PNG → Unity 导入为贴图 + 材质** | 与图形设备完全解耦，批处理随时可跑；一次写好可批量扩到 500 字 | 字形源是 OS 字体文件，脱离 Unity 资产库（见「后果」） |
| D. 手绘 / AI 生成字图 | — | 与 ADR-0003 冲突：风格一致性不可控，且成本高 |

---

## 决策（Decision）

**选择方案 C**，具体形态：

1. `Tools/glyph_bake.py` 用 Pillow 从字体文件把字符串烘成**透明底白字 PNG**，每字占一格正方形。
   - `兵` → `tex_glyph_bing.png`（128×128，单字）
   - `英雄` → `tex_glyph_hero.png`（256×128，两字横排 → 天然就是「两个字的单位」）
2. `GlyphAssetBuilder`（Editor）负责把 PNG 按透明底规格导入，并创建启用 instancing 的材质。
3. `GlyphInstanced.shader` 负责渲染：AlphaTest(cutout) + `multi_compile_instancing`。
   - 选 cutout 而非半透明混合：字形之间不需要排序，`ZWrite` 可开，instancing 友好。
   - **`Cull Off` 是必需的**：俯视相机看到的是 quad 背面，开着剔除整片字潮会消失。
4. 颜色不进贴图，走材质 `_Color` 染色 → 一张贴图可复用于多种染色（未来敌我双方共用字库）。

**为什么单字贴图不需要 per-instance UV**：这一刻的一千个单位**都是同一个「兵」字**。
同字 = 同一张贴图 = 零 per-instance 数据，这是当前阶段最快也最简单的形态。
多字混排是后续问题，见「复核条件」。

---

## 后果（Consequences）

### 正面

- 渲染与图形设备解耦，`-nographics` 批处理能稳定复现
- 单批次上限 1023（C4.3），1000 个「兵」一批画完
- 贴图体积极小（「兵」1.5 KB / 「英雄」4.3 KB），远低于 C2.5 的 80 MB 预算
- 字形烘焙脚本可复用：改 `--glyph`/`--size` 就能扩字库，是 `AtlasBaker` 的雏形

### 负面 / 需要接受的代价

- **字形源脱离 Unity 资产库**：当前用 `C:\Windows\Fonts\msyhbd.ttc`（微软雅黑 Bold）。
  C3.3 的「字形源唯一」在精神上满足（单一字体），但载体不是 TMP 字体资产。
- **⚠ 字体授权是商用阻断项**：微软雅黑**不可商用分发**。上架前必须换成开源字体
  （思源黑体 / 霞鹜文楷 / Noto Sans SC，均为 OFL），重新烘焙即可，技术成本接近零。
- 目前只有**静态字形**，没有序列帧动画。C2.2（4-6 帧循环）尚未满足。
- 每个新字都要单独烘焙一张贴图——字库到 200+ 时必须改成**图集（Atlas）+ per-instance UV**，
  现在这个「一贴图一字」的形态只在「全场同一个字」时成立。

### 后续动作

- [ ] 上架前把字体换成 OFL 开源字体并重新烘焙
- [ ] 字库扩到多字时，改图集 + per-instance UV（`MaterialPropertyBlock` 传 UV 索引）

## 复核条件（何时重新评估）

- 同屏出现**两种以上**不同的字 → 单贴图方案失效，必须转图集
- 需要字形动画（摆动/燃烧/碎裂）→ 转到 sprite sheet + UV 动画
- 要上架商用 → 字体授权必须先解决
