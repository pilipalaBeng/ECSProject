# 无头验证通道（batchmode + 自检）

MCP 只在编辑器 GUI 开着时可用。批处理通道是它的补充：不开界面也能编译、建场景、跑逻辑自检。
两者不冲突，反而互补——**改代码走批处理验证，调场景走 MCP**。

## 1. 标准命令

```bash
cd "D:/Project/Project Unity/ECSProject" && \
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
"D:/Software/Unity/Unity/UnitySetup64-2022.3.62f1/Editor/Unity.exe" \
  -batchmode -nographics -quit \
  -projectPath "D:/Project/Project Unity/ECSProject" \
  -executeMethod <方法全名> \
  -logFile Logs/<名字>.log
```

`<方法全名>` 现成的四个：

| 方法 | 作用 |
|---|---|
| `HanziRogue.Editor.SceneBuilder.Build` | 生成单场景 `MainScene`（MetaRoot / BattleRoot 双模式）并写入 Build Settings |
| `HanziRogue.Editor.SceneFlowSmokeTest.Run` | 局内局外往返自检（Enter→Exit→Enter），报告落盘 `Logs/sceneflow_report.txt` |
| `HanziRogue.Editor.BoidsSmokeTest.Run` | 建临时 World 跑 Boids，验证环形生成/无重叠/合围/边界 |
| `HanziRogue.Editor.GlyphAssetBuilder.RebuildAll` | 从烘焙 PNG 重建字形材质 |

字形贴图本身由 `Tools/glyph_bake.py` 离线生成（不是 Unity 方法）：

```bash
python Tools/glyph_bake.py --out Assets/_HanziRogue/Data/Glyphs --glyph 兵 --cell 128 --size 112 --name tex_glyph_bing
python Tools/glyph_check.py Assets/_HanziRogue/Data/Glyphs/*.png   # alpha 自检，防止烘出空图
```

## 2. 四个必踩的坑（都花过时间）

**① 必须清代理 + 非沙箱**
本机 shell 带 `HTTP_PROXY` 指向沙箱端口，Unity 的联网请求会被挡（`Curl error 28 timeout`）。
两个条件缺一不可：`env -u HTTP_PROXY...` 且工具调用加 `dangerouslyDisableSandbox`。

**② 同一工程只能有一个 Unity 实例**
残留进程会导致 `HandleProjectAlreadyOpenInAnotherInstance` 崩溃，表现为 `EXIT=1` 且日志里没有任何 `error CS`。
遇到 `EXIT=1` 先 `taskkill //F //IM Unity.exe`，必要时删 `Temp/UnityLockfile`。

**③ 装 UPM 包尽量走 embedded**
git URL 拉包会被代理卡死。做法：从别的项目 `Library/PackageCache/` 复制包目录到本工程 `Packages/`，
Unity 会自动识别为 embedded 包，零网络。（unity-mcp 就是这么装的，见 `unity-mcp-接入.md`）

**④ 编辑器窗口不在前台时，主循环几乎不走**

这是 MCP 通道最阴的坑，表现为「代码明明没问题，敌人却一动不动」。

实测数据（2026-10-07）：进 PlayMode 后等了约 60 秒，`Time.frameCount` 只有 28，`Time.time` 只有 **0.071 秒**。
原因是 Unity 在窗口未激活时基本不泵编辑器循环，只有收到 MCP 请求时才被唤醒跑几帧。

连带的第二个症状：**`AssetDatabase` 也不会自动刷新**——
改完 `.cs` 后 `isCompiling` 一直是 `false`，你会一直跑到旧编译的可执行代码上，
看到「改了没效果」甚至「新加的日志不打印」，非常容易误判成逻辑 bug。

两个对策：

```csharp
// 1) 改完代码先强制刷新，再等编译，再验证
UnityEditor.AssetDatabase.Refresh(UnityEditor.ImportAssetOptions.ForceUpdate);
// 返回后查 isCompiling；为 true 就等它变 false 再往下

// 2) 需要「推进游戏时间」时，不等主循环，直接手动步进
var world = Unity.Entities.World.DefaultGameObjectInjectionWorld;
float dt = 1f / 60f;
for (int i = 1; i <= 300; i++)
{
    world.SetTime(new Unity.Core.TimeData(i * dt, dt));
    world.Update();
}
```

手动步进 PlayMode 的默认 World 是安全的（同步执行、主线程），不会与 PlayerLoop 打架。

## 3. ECS 自检的坑：GetOrCreateSystem 不会自动挂进 group

`world.GetOrCreateSystem<T>()` **只创建系统，不会把它加进所属 group 的 update list**。
结果是 `world.Update()` 空转，实体一个不生成，且不报错——非常难查。

正确写法：

```csharp
var simulationGroup = world.GetOrCreateSystemManaged<SimulationSystemGroup>();
simulationGroup.AddSystemToUpdateList(world.GetOrCreateSystem<EnemySpawnSystem>());
simulationGroup.AddSystemToUpdateList(world.GetOrCreateSystem<BoidsSystem>());
```

> 真实运行时不受影响：`DefaultGameObjectInjectionWorld` 由 Entities 自动引导创建，系统挂载是自动的。
> 只有**手动 new World** 做单元测试时才需要显式挂载。

## 4. 其他零散坑

| 现象 | 原因 |
|---|---|
| 代码里中文注释用了半角 `"` | 会把 C# 字符串提前截断，报 `CS1003 , expected`。注释内用「」 |
| `EntityQuery.IsCreated` 不存在 | Entities 1.0 的 EntityQuery 没这个成员。用自己维护的 bool 标志代替 |
| `TimeData` 找不到 | 它在命名空间 `Unity.Core`，要 `using Unity.Core;`。程序集不用额外引（`Unity.Core` 通过 asmref 挂在 Unity.Entities 上） |
| Editor asmdef 找不到 Entities | 需要显式加 `Unity.Entities` / `Unity.Mathematics` / `Unity.Collections` 引用 |
| **1000 个单位全生成在同一个坐标** | `Unity.Mathematics.Random` 是 struct，当参数**按值传递**时状态被拷贝，每次调用都从同一起点取数。必须 `ref Random rnd` |
| 俯视相机下整片 quad 消失 | 自定义 shader 没写 `Cull Off`，俯视看到的是背面。 |
| AlphaTest 的实例化字看不到 | 顶点着色器漏了 `UNITY_SETUP_INSTANCE_ID(v)`，`UnityObjectToClipPos` 拿不到 per-instance 矩阵，所有实例叠在原点。 |
| `Object` 在 execute_code 里报歧义 | Unity 的 execute_code 同时可见 `object` 与 `UnityEngine.Object`，要写全 `UnityEngine.Object` |
| 按 `world.Systems` 枚举**找不到自己的系统** | 它只返回**托管**系统（`ComponentSystemBase`）。本工程全部是 unmanaged `ISystem`，一个都不在里面。正确查法：`world.Unmanaged.GetExistingSystemState<T>()`，返回的 `SystemState.Enabled` 可读开关 |
| execute_code 里写局部函数报 `Keyword 'void' cannot be used in this context` | MCP 的 execute_code 走 CodeDom，只认老 C# 语法。递归遍历改成显式 Queue 循环 |
| shader 的 `Properties` 里写 `[Header("…")]` 解析失败 | 报 `Parse error: syntax error, unexpected $undefined, expecting TVAL_ID or TVAL_VARREF`。**中文注释与中文字符串都没问题**，是 `[Header]` 标签不被 shader 解析器接受，分组只能用 `//` 注释代替 |
| 改完 `.shader` 后 `Shader.Find` 返回 null | 同样是「刷新要等编辑器循环」。对策：`AssetDatabase.Refresh()` 后改用 `AssetDatabase.LoadAssetAtPath<Shader>(path)` 强制加载。**shader 是资源、不需要 C# 编译**，所以编辑器卡在编译态时它仍然可用——这是绕过卡死的一根救命绳 |

> 「叠在同一点」那条的教训值得单独记：当时 1000 个实体叠成一坨，
> 而「数量对 / 无 NaN / 距离下降」三条断言**全都通过**。
> 断言必须覆盖**分布**，不只是**数量**——这就是 `MinPairwiseDistance` 存在的原因。

## 5. 渲染取证：把画面导成 PNG 再肉眼确认

逻辑自检通过 ≠ 画面是对的。字形方向、UV 翻转、剔除、材质装配，这些只有看图才能确认。

在 PlayMode 下用 MCP 取证的标准套路（手动步进 + 离屏渲染 + 落盘）：

```csharp
// 1) 推进若干帧（编辑器后台不跑循环，见 §2 坑④）
// 2) 手动跑一遍表现层：MonoBehaviour 的 Update 不会因为 world.Update() 被调用
GameObject.Find("Hero").SendMessage("Update");
GameObject.Find("EnemyRenderer").SendMessage("Update");

// 3) 离屏渲染到 RenderTexture 再读回
var cam = Camera.main;
var rt = new RenderTexture(1280, 720, 24);
cam.targetTexture = rt;
cam.Render();
RenderTexture.active = rt;
var tex = new Texture2D(1280, 720, TextureFormat.RGBA32, false);
tex.ReadPixels(new Rect(0, 0, 1280, 720), 0, 0);
tex.Apply();
RenderTexture.active = null;
cam.targetTexture = null;
System.IO.File.WriteAllBytes("Logs/shot.png", tex.EncodeToPNG());
```

三条注意：

- `Graphics.DrawMeshInstanced` 提交的是**当帧**绘制命令，`cam.Render()` 能复现；
  但**不会**因为 `world.Update()` 而自动重算，所以要手动 `SendMessage("Update")`。
- **视野外的实体拍不到**。第一次取证时 1000 个敌人全在半径 48 米的环上、
  而近景正交半径只有 18 米，截图里一片空——那不是渲染坏了，是没东西在画面里。
- 相机若挂了跟随组件，截前先手动把 `cam.transform.position` 摆到目标处，
  否则它会用极小的 `Time.deltaTime` 慢慢爬过去。
- **`cam.Render()` 拍不到 IMGUI / OnGUI**。HUD 走 IMGUI（为免引 UGUI 包），
  所以取证图里永远看不到 HUD —— 别误判成「HUD 没渲染」。要验 HUD 只能人眼看 Game 视图。
