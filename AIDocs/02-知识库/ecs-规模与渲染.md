# ECS 规模与渲染知识库

> **L2 参考层**。本项目的技术底座知识。数字凡标 `[待实测]` 者未经本项目验证，不得当作既有事实引用（宪法 §4.8）。

## 1. 核心结论：十万是数字，不是实体

玩家的"十万大军"感受由**累计击杀计数器**承担，不由场景对象数承担。
行业惯例佐证：真三国无双同屏敌人通常只有几十个，但击杀计数能上四位数，玩家普遍相信自己在"一骑当千"。**玩家信数字，不信眼睛数出来的。**

这意味着：你不需要优化到十万实体，你需要的是**三层 LOD + 一个诚实的计数器**。

## 2. 三层 LOD 表现方案

> **主源声明**：下表数字引自 `01-治理/CONSTRAINTS.md` C1（唯一主源）。本表只解释「为什么这么分」，改数字请改 C1。

| 层 | 距离 | 实体数 | 约束编号 | 渲染方式 | 可交互 |
|----|------|--------|----------|----------|--------|
| 近场 | 0-8 m | 500 - 1,500 | C1.3 | 独立字牌，完整序列帧 + 碎裂动画 | 是（可单独击杀） |
| 中景 | 8-25 m | 5,000 - 15,000 | C1.2 | 聚合字块（「兵 ×327」），instanced | 否（范围伤害仍生效） |

真实实体总量 = **5,500 - 16,500**（上限见 C1.1），即 ECS 甜区。GM 拍脑袋说「要十万」时，用这张表回答。

## 3. 为什么不能用 TextMeshPro 渲染战场

| 问题 | 后果 |
|------|------|
| 每个 TMP 组件至少 1-2 个 draw call | 万级实体 = 万级 draw call，必崩 |
| Glyph atlas 动态扩容 | 运行时生成字形会卡主线程 |
| TMP 是 UI/文本组件，非 instancing 友好 | 无法批量绘制 |

**结论**：战场文字**必须**走自定义 instancing 管线（CONSTRAINTS C4.1）。TMP 只在两处使用：HUD 文本、字形源导出。

## 4. Sprite Sheet Instancing 原理

字潮与精锐层的渲染方案（CONSTRAINTS C4.2）：

1. 把所有字形 + 动画帧烘焙进一张 sprite sheet
2. 所有实体共用同一 material
3. 每个 instance 携带：`position`、`frameIndex`（当前帧）、`uvRect`（字形在图集中的位置）、`color`、`alpha`
4. Shader 内根据 `frameIndex` 计算 UV 偏移，实现序列帧动画
5. 一次 draw call 绘制数千个 instance

**关键 API 约束**：`Graphics.DrawMeshInstanced` 单次上限 **1,023** 个实例，超出必须分批（C4.3）。若用 `BatchRendererGroup`（Entities Graphics 底层）则无此限制，但实现复杂度更高。

**文字媒介的隐藏优势**：3D 割草难做 instancing 是因为模型/贴图种类多；而字库只有几百种，一张图集装得下。这是文字游戏少有的技术红利。

## 5. 美术生产管线（程序化，禁止 AI 生成资产）

```
TMP 字体资产（确定的源字形）
   ↓  程序化变形：摆动 / 缩放 / 燃烧 / 笔画分离
烘焙 sprite sheet（Editor 阶段，200-500 字 × 8 帧）
   ↓
GPU instancing（单批次数千）
```

**为什么这条管线解决了美术难题**：
- 源字形是确定的（同一套字体），不存在风格漂移
- 变换是程序化的，可批量、可复现、可参数化调整
- **不需要 AI 生成任何美术资产**，因此没有"十个字十个风格"的一致性灾难（宪法 §2.3）

**击杀特效**：预烘焙"字碎裂"序列帧 —— 完整 → 裂开 → 笔画飞散 → 消散，**6 帧**（C4.5）。
比实时笔画粒子系统便宜一个数量级，且视觉更可控。
"笔画拆解飞散"是汉字独有的击杀反馈，英文做不到 —— 这是 pillar 4「每个字死得有样子」的落地。

**内存预算**（C2）：
- 单字 64×64 RGBA = 16 KB/帧
- 8 帧 = 128 KB/字
- 200 字 ≈ 26 MB（安全）· 512 字 ≈ 65 MB（可行）· 1024 字 ≈ 131 MB（危险）
- 故字库硬封顶 **500 字**

## 6. 邻近查询：必须空间分区

万级实体的伤害范围判定若走 O(n²) 全量遍历，必崩（CONSTRAINTS C1.8）。

**方案**：16×16 网格空间分区。每个实体按位置落入网格单元，范围伤害只查询覆盖到的单元及其邻域，复杂度降到 O(n·k)，k 为邻域常量。

**注意**：网格分辨率是 tuning lever，不是常量。格子太大 → 单格实体过多退化成 O(n²)；太小 → 查询跨格过多。初始 16×16 [待实测]，需按实际战场尺寸调整。

## 7. 热路径清单（这些地方每帧跑万次）

| 系统 | 约束 |
|------|------|
| 移动/寻路 | 零堆分配，Burst 编译 |
| 伤害结算 | 走空间分区，禁止全量遍历 |
| 序列帧推进 | 只写 `frameIndex` 到 buffer，不碰 GameObject |
| 实体回收 | 用对象池 / Entity 复用，禁止频繁 Create/Destroy |

**Burst 兼容红线**（C5.1）：`IComponentData` 内禁止 managed 类型（class / string / 数组 / 委托）。需要字符串 → 存索引查表。

## 8. 常见坑（预登记，踩到就补这里）

| 坑 | 现象 | 对策 |
|----|------|------|
| 运行时生成图集 | 主线程卡死数秒 | 强制 Editor 预烘焙（C2.6） |
| 生僻字渲染不出 | 空白/豆腐块 | 字体覆盖检查 + fallback 字体链（C3.4） |
| 中景播全套碎裂动画 | 特效噪声淹没信息 | 中景走简化淡出（C4.6） |
| System 里访问 Transform | Burst 编译失败 / 性能崩 | 逻辑表现分离（宪法 §3.1） |
| 单次 instancing 超 1023 | 部分实体不渲染 | 分批（C4.3） |
| 组件里放 string | Burst 编译失败 | 存索引（C5.2） |
