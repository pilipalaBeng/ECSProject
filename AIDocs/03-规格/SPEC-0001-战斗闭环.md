## 1. 目标与非目标

**目标**：英雄能攻击「兵」，兵有血量、受击闪白、死亡；英雄有血量、受击闪红；英雄有一个粗糙的持枪前刺动画。

**本次不做**（明确切走，避免范围膨胀）：五行相克、词条、死亡碎裂序列帧、波次生成、正式数值 UI（本次只做 IMGUI 文本）。

理由：这五项每一个都要单独开 ADR，塞进来会让本次改动失去可验证性。

## 2. 现状诊断：为什么不能往现有代码里直接塞

| 现状 | 问题 |
|------|------|
| `InstancedEnemyRenderer` 用 `Graphics.DrawMeshInstanced` + 单一材质 | **拿不到 per-instance 数据**。受击闪白要按个体染色，这条路走不通（详见 D3） |
| `EnemySpawnSystem` 用「场上还有没有敌人」判断要不要生成 | **引入死亡后，杀光最后一波会立刻重刷一整波**（详见 T1） |
| `HeroInput` 只有 Move 一个字段 | 后续加闪避/切字会持续往里塞字段，形成「意图万能组件」 |
| 伤害没有宿主：谁来扣血没有定义 | 若让攻击方直接写 `Health`，则「吸血」「反伤」「相克倍率」将来要在每个伤害源里重复实现 |

## 3. 关键架构决策

### D1 · 伤害走事件队列，`ApplyDamageSystem` 是全工程唯一的 Health 写入点

```
生产者（只算「谁该掉血、掉多少」）
    HeroAttackSystem   → DamageEvent(target=某兵, amount)
    EnemyAttackSystem  → DamageEvent(target=英雄, amount)
消费者（唯一写 Health 的地方）
    ApplyDamageSystem  → 扣血 / 写 HitFlash / 判死 / 累加击杀
```

**为什么不让攻击者直接扣血**：一旦有第二处写 `Health`，将来每一个跨系统效果（吸血、反伤、护盾、相克倍率）都要在每一处重复一遍，且漏一处就是静默 bug。单一写入点是让「低层 armor 以后能接进去」的前置条件。

**开销**：`NativeQueue<DamageEvent>` 只在「有命中的那一帧」才产生条目，量级是每帧几十~几百条。可忽略。

**为什么不用 NativeArray 裸列表**：多个生产者 job 并行追加会写冲突。队列用 `ParallelWriter` 生产、单条 consumer job 消费，是 ECS 里的标准解法，且 Burst 全程兼容。

### D2 · 命中判定走 O(n) 单中心查询，**不**复用 `SpatialGrid`

攻击/接触判定都以「单个中心（英雄）」为圆心，不是两两配对邻近查询，复杂度是 **O(n·1)**，不满足 C1.8 禁止的 O(n²)。1000 个敌人在 Burst job 里做一次距离/矩形判断是微秒级，而攻击判定平均 **每 0.35 秒才触发一次**。

把 `SpatialGrid` 提升成跨 System 共享状态，要付出「谁建谁销毁、System 排序依赖、搬运 struct」的代价，换来的收益接近零。**这是本方案里最重要的一条「不要过度工程」判断。**

> **未来切换门槛（写在这里，别到时候重讨论）**：当 `EnemyCount > 5000` 或「每秒攻击次数 > 10」时，改为在 `SpatialGrid` 上做 3×3 单点查询。

### D3 · per-instance 染色：渲染通道必须升级到 `DrawMeshInstancedIndirect`

| 方案 | 做法 | 判断 |
|------|------|------|
| A. `DrawMeshInstanced` + `MaterialPropertyBlock` | 两个批次，正常 vs 闪白 | ❌ MPB 只能给整个批次统一赋值，**做不到 per-instance**。同一帧受伤的兵只能用同一条淡出曲线，不同时刻受伤的兵亮度会同步跳变 |
| B. `DrawMeshInstancedIndirect` + `StructuredBuffer` | 每实例数据进 ComputeBuffer，shader 按 `SV_InstanceID` 索引 | ✅ **推荐** |
| C. 引入 `com.unity.entities.graphics` | 走 Entities Graphics 的 DOTS instancing | ❌ 包未安装，Built-in 管线 + Entities 1.0 的接入成本高，收益与 B 相同 |

**选 B 的真正理由不是闪白本身**：C4.5（击杀特效 6 帧序列帧）与 C4.2（sprite sheet UV 动画）都在路线图上，它们同样需要 per-instance 的 UV 偏移参数。B 是唯一一条能一路走下去的路，顺带消除 C4.3 的 1023 分批限制。

### D4 · `Health` 用 `float`，不用 `int`

用户给的是整数（10 血 / 5 伤），但宪法 §2.5 规定「五行相克是唯一伤害规则」——相克倍率 **1.0 / 3.0 / 0.4** 一旦接入，伤害必然变成小数（`5 × 0.4 = 2` 看着是整数，但 `3 × 3.0 = 9`、`7 × 0.4 = 2.8` 不是）。用 int 会在接相克时被迫改组件类型，那是波及全部引用的破坏性改动。

### D5 · 引入 `BattleProgress` singleton，替代「有没有敌人」判据

同时承载：本局是否已生成过（`SpawnDone`）、击杀计数（`KillCount`、含上限保护）。
由 `BattleSession` 与 `GameConfig` 一起创建，随 Purge 一起销毁。

### D6 · 意图组件收敛为 `HeroIntent`

`HeroInput` 改名为 `HeroIntent`，字段 `{ Move, Attack }`。现在改名成本是 3 处引用；等加了闪避/切字再改就是几十处。

## 5. 攻击形状与状态机

**攻击判定时机**：只在 **Active 进入的那一帧**做一次判定（不是持续几帧），天然幂等，不需要「同一刀去重」的额外组件。

**形状**：以英雄中心为原点、沿 `Facing2D` 延伸 `Reach` 米、宽度 `HalfWidth` 米的胶囊（点到线段距离 ≤ r）。单次攻击穿透上限 `PierceCap` 个目标，按离英雄由近及远取用。

**相位**：

```
Idle ──按下攻击──▶ Startup(0.10s) ──▶ Active(单帧) ──▶ Recover(0.18s) ──▶ Idle
                    收枪蓄势            突刺+判定          收枪
```

**表现层如何知道该画什么**：`HeroAttackState.Phase + Timer` 是纯数据，`HeroWeaponView` 按相位把枪插值到前伸位置。**逻辑不认识动画，动画不认识伤害**——二者只通过这两个 float 通信。

## 10. 实施回填（2026-10-07）

### 10.1 与本文不一致的地方（**以实际实现为准**）

| # | 本文原方案 | 实际做法 | 为什么改 |
|---|-----------|---------|---------|
| 1 | `Components/Damage.cs` 定义 `DamageEvent{Target, Amount, SourceKind}`，用 `NativeQueue<DamageEvent>` 传递 | 改为 `PendingDamage` **每实体累加器**，定义在 `Combat.cs` | 实施时发现两个伤害源的**目标集天然不相交**（英雄只写兵、兵只写英雄），每个实体的累加器全局只有一个写入方 → 既不需要原子操作，也不需要队列。共享 `NativeQueue` 要额外付出生命周期管理与依赖排序，换来的只是「形式上是事件」的观感。**这是有意的简化，代价是「同一目标集只有一个伤害源」这条不变式只能靠注释约束**。详见 ADR-0014 决策 3 |
| 2 | `Core/CombatPhase.cs` 单独一个文件 | 合进 `Combat.cs`（`AttackPhase` 静态常量类） | 4 个 byte 常量单独占一个文件，找起来反而更麻烦 |
| 3 | `Gameplay/EnemyDeathSystem.cs` 单独一个系统 | 没有这个系统；死亡销毁在 `ApplyDamageSystem` 的 ECB 里 | 判死与销毁本来就是同一件事的两半，拆成两个系统只会让「谁负责判死」变模糊 |
| 4 | `Presentation/HeroView.cs` 改（增加朝向同步） | `HeroView` 未动；武器动画放在新增的 `HeroWeaponView` 里 | 英雄字形的朝向同步不是武器动画的前提——武器节点自己按 `Facing2D` 定位即可，`HeroView` 少改一处就少一份回归风险 |
| 5 | `HeroRecoverTime = 0.18 s`（§6 N5.6） | 实际 **0.20 s** | 取整到 0.2 让「循环 = 0.30 s」这个数好记；已在 `数值预算表.md` §5 按 0.20 登记 |
