### 起源
用户看到《赵云与阿斗》（北京蜜獾工坊，2026 年 6-7 月霸榜微信小游戏畅玩榜/人气榜/PC 榜，IAA 变现，合成+塔防+1v1 对称对抗，单局 5-10 分钟）后，想做文字类游戏规避 AI 美术难题，考虑做成肉鸽 + Unity ECS。

### 第一轮判断（已被部分推翻）
- 活检结论：《赵云与阿斗》的护城河是「汉字即机制」（单字=单位、偏旁=攻击表现、专名=收集钩子），不是「省美术」。
- 原判断：ECS 在文字肉鸽下是过度设计（实体规模小、UI 占 60% 工、UI Toolkit 无官方 ECS 绑定）。
- 参考竞品：《Text Dungeon: The Ring of Life》（Steam 2026-09，预估 5952 wishlist / rank #5177）、乙一用 Claude Code 做的免费《Minimal Rogue》（2026-08，itch.io，MIT 开源，100 层 3-5 小时）。

### 第二轮：用户新增关键约束 → 结论修正
用户明确要「怪很多 / 曹操十万大军 / 真三国无双割草感 + 本质肉鸽」。ECS 由此获得正当理由。

**最终设计方向（待用户确认平台）**
- Fun hypothesis：用正确的字，把一整片错误的字扫成漫天笔画。
- Design pillars：数字即画面 / 一秒一个决策 / 对的时候要碾压 / 每个字死得有样子。
- 核心玩法：五行相克字——敌方字潮带五行属性（木林森/火炎焱/土城垒/金鑫锋/水淼江涛），玩家持字武器切换，相克 ×3.0、逆属性 ×0.4、切字 CD 1.5s。割草释放期 30-60s 一波，波间 20-40s 三选一构筑。
- 肉鸽层：汉字合成树（火+火=炎，炎+火=焱；木+木=林，林+木=森）天然即 build 树，中文母语者先验知识省掉教学成本。英文做不到，是真正差异化。

**关键技术判断（重要，别忘）**
- 「十万」不需要十万实体。三层 LOD：近场 0-8m（500-1500 真实体，独立字牌+笔画拆解粒子）/ 中景 8-25m（5000-15000 真实体，聚合渲染「兵 ×327」）/ 远潮 25m+（0 实体，密度场 shader）。真实实体总量 5500-16500 = ECS 甜区。十万感由 UI 击杀计数器承担（真三同屏也就几十个敌人，玩家信数字不信眼睛）。
- **不能用 TextMeshPro 逐个渲染**（一万字必崩）。必须自研 instanced text renderer：汉字预烘焙 glyph atlas（2048²/64px → 1024 字；4096² → 4096 字），BRG 或分批 DrawMeshInstanced（单次上限 1023）。文字媒介反而比 3D 更好 instancing，因为字库种类有限。
- 因此 UI Toolkit 的 ECS 集成问题被绕开——战场字走自研渲染器，UI 只剩 HUD。
- 架构：Entities + Burst + IJobEntity（16×16 网格空间分区做邻近查询，避免 O(n²)）→ NativeArray 桥接 → GPU instanced 渲染 → GPU 笔画粒子 → UI Toolkit 仅 HUD。
- 中文字形图集必须预烘焙，运行时动态生成会卡死。

**风险**：自研渲染器是最大工程量；AI 生成 200+ 词条的语感风险仍在。

**验证路径（已定义失败信号）**
1. 技术验证优先：5000 汉字 instanced demo 跑 60fps，不通过则后面全废。
2. 手感原型：固定 build 割 3 分钟。
- 失败信号 A：5000 字 <30fps → 渲染方案重做
- 失败信号 B：玩家说「只是在看数字涨」→ 反馈通道不足（加笔画密度/震屏/数字弹跳），非机制问题
- 失败信号 C：三选一时「选哪个都无所谓」→ 词条差异化不足，需重做

### 待用户确认（会改变方向的项）
1. 平台：默认假设 Steam PC。若微信小游戏，规模需砍到 1/10，设计逻辑完全不同。
2. 先做技术验证 demo 还是先写 GDD？我的建议：先跑 demo，5000 字这关过了再写文档。
3. 单局时长假设 20-30 分钟（3-4 关 × 5-8 波），若实测 >40 分钟难度曲线要重画。

### 第三轮修正：美术走序列帧
用户明确「实体都是序列帧而已，英雄单位可以是复杂一点的动画单位」。这条修正比表面更重要：

## 追加（15:05~）：追击算法改造 = ADR-0008（用户反馈「追溯算法不是很好」）

### 诊断：不是调参问题，是算法选错了
原来是完整 Boids 四力（分离 1.6 / 聚合 0.5 / 对齐 0.8 / 追击 2.2）+ 加速度积分（`vel += accel*dt`，无阻尼）。四个毛病：
1. **聚合 + 对齐 → 绕着玩家盘旋**。这两项是为鸟群自组织设计的，敌人有唯一目标时它们就是纯粹的干扰。
   **上一轮取证截图里我观察到的「旋臂结构」就是它——当时误判成了待调观感问题，其实是算法错。**
2. **加速度积分无阻尼 → 过冲漂移**，观感像飞船不是咬人的敌人。
3. **分离力 normalizesafe 后丢掉距离信息** → 只要有一个邻居就全力推开，来回抖。
4. **全场同速 8 m/s** → 一千个字像刚性板整体平移，没有字潮层次。

### 行业对照（幸存者类）
追击就是三件事：**seek + 防重叠 + 转向平滑**。不做寻路、不做群体自组织。
- Construct 社区复刻讨论：VS 敌人「move as Bullet」（朝玩家直线匀速），重叠用「simple push」解决
- GitHub 的 C++ 复刻：`dir = normalize(player - pos); pos += dir * moveSpeed`（纯 seek，四行）
- GameMaker 复刻：「only need a direction where to go and a speed value」
- 中文 Unity 复刻复盘：**每帧直接把速度朝玩家拉会「集体抽搐式转向」**，所以要限制转向角速度（turnSpeed 3~5 弧度/秒），且 `velocity = newDir * moveSpeed`（**直接设速度，不是积分**）

### 实施（代码已写完，验证未跑）
- `BoidsJob` 重写：`desired = normalize(seek + separation)`；`RotateTowards(current, desired, TurnRate*dt)`；
  `vel = dir * moveSpeed`（per-entity，不再用全局 MaxSpeed）
- 分离力改为按 `(1 - d/r)` 线性衰减，不再 normalize
- 聚合/对齐默认 0，`needFlock` 短路连累加都跳过（不为零成本的东西付账）
- 新增 `TurnRate = 5`、`SpeedVariance = 0.12`；生成时每个兵 ±12% 速度（**复用已有 MoveSpeed 组件，不加新组件**）
- `BoidsSmokeTest`：**改为从 ScaleConfig.asset 读配置**——原来硬编码 `SeparationRadius=0.8` 而实际运行是 1.15，
  等于自检验的根本不是真配置。新增「贴身敌人数（< 1.5m）」断言：绕圈式追击下这个数恒为 0，专门抓「追而不咬」
- `ADR-0008` + 数值预算表 N4.7 改 / N4.9 / N4.10 新增

### ⚠ 状态：编辑器卡在编译态，验证未跑
`isCompiling=True` 持续 7 分钟、程序集里没有 `TurnRate` 字段、`isPlaying=False`（play 请求进不去）。
`AssetDatabase.Refresh(ForceUpdate)`、`RequestScriptCompilation`、`UnlockReloadAssemblies`、切 Play 都无效；
COM `AppActivate` 激活窗口被安全策略拦。**根治办法只有人工点一下 Unity 窗口**（后台不推进循环的老坑）。

### 关于「幸存者类是 ECS 实现的吗」
答：**追击算法与 ECS 正交**——同一套数学，OOP 写在 `Enemy.Update`，ECS 写在 `IJobEntity.Execute`。
公开可见的复刻（GameMaker / Godot / Construct / C++）全是传统对象模型，不是 ECS。
ECS 的价值只在规模（并行 + 缓存友好）：几百个敌人对象池就够，上万（本项目 C1.1 上限 16500）才需要。
弹壳特攻队的内部架构用户比我清楚（他做过），未下断言。

### 决定性发现：`NeighborData` 没有身份字段 → 每个兵在推自己

`NeighborData` 原来只有 `Pos` / `Vel`。空间哈希网格把每个兵自己也写进去，
`NeighborPush` 迭代时**分不清「我」和「邻居」**：
网格存的是**帧初**位置，计算用**帧末**位置，两者差本帧位移 ≈0.13 米
→ 每个兵都检测到「一个离我 0.13 米的邻居」，**沿自己运动方向给自己加 0.5 米推力**。
单帧推力上限只有 `SeparationRadius × 0.5 = 0.575` 米，**伪推力把预算吃干**，真邻居互推全被限幅砍掉。

**这就是「字间距怎么调都糊」的真凶**，之前三轮（二值阻挡 / 硬挤 / 侧移）全在治标。
修法：`NeighborData` 加 `Index = entity.Index`，循环里 `if (n.Index == selfIndex) continue;`；
`LocalRoom` 的邻居计数同样要排除自身，否则永远少算一个空位。

**顺带破了一桩旧案**：早前 `ResolveOverlapJob` 用 `ScheduleParallel` 时「看起来不执行」，
其实是我自己那段临时诊断探针在**并发写同一个 NativeArray**、触发作业安全系统。
诊断代码清掉后 `ScheduleParallel` 正常工作，不需要 `.Run()` 强制同步。

### 最终机制（三件事缺一不可）

1. **抵达系数** `saturate((dist-StopRadius)/(ArriveRadius-StopRadius))`
   —— 进 `StopRadius` 后推进力归零，除掉绕圈的物理根源（旧版追击力永不消失，只能沿环滑）。转向半径 8/5=1.6 米，光靠转向永远转不过来。
2. **局部密度节流** `room = saturate(1 - 邻居数/SeparationRadius内 / 6)`
   —— 6 是二维六方密堆容量。用**连续**的邻居数取代二值的「前方有人就停」（那个会连锁冻结到 20 米外，实测平均距离卡在 22.7 米）。
   `approach = arrive × room`，相乘不是取小。
3. **位置层硬约束** `ResolveOverlapJob`（松弛 0.5 + 单帧限幅 `SeparationRadius×0.5`，每帧 **2 遍**近似 Gauss-Seidel）
   —— 速度层分离力是软约束，密度一高压穿（实测最近 0.03 米）。英雄硬核用**投影**不用加力（力会被邻居合力抵消，投影不会）。
   松弛给满 1.0 会过冲：全群 2 秒跑出 24 米，比速度上限还快。

### 关键几何账（已写进 ADR-0010，别再重推）

- 英雄硬核 0.9 米 → 一圈周长 5.65 米，按间距 1.15 只站得下 **5 个兵**；0.9~2.0 米环带只容 **8.75 个**。
  实测曾挤进 127 个（超容量 14 倍）——**不是参数问题，是物理上不可能**。
- 1000 个兵按 1.15 间距自然密堆需 `1000×1.145≈1145 m²` → 半径约 **19 米的圆盘**，平均距离下界 ~12.7 米。
- ⚠ **平均值不是「越小越好」**：改后平均距离 11~24 米看着比改前的 3.7 米「远」，
  但改前那个 3.7 是病态压缩（间距 0）的副产物。**判据只能是「贴身区最小间距 + 贴身人数 + 静止漂移」三条**，单看平均距离会被带偏（本次为此改过三次方向）。

## 追加（17:12）：十万实体卡顿归因（用户猜 drawCall，实际不是）

用户问「ECS 不是性能最好吗？改到十万为什么卡？是不是 drawCall 的问题」。

### 结论：不是 drawCall，是邻域查询的 k 从 10 变成了 1062

**渲染侧（用户猜的方向）**：100000 / 1023 = **98 个 draw call**，GPU 侧毫无压力。但 `InstancedEnemyRenderer.Update()` 主线程确实有开销：100000 次 `Matrix4x4.TRS` + 每帧 `ToComponentDataArray(TempJob)` 强制同步 job + 98 次 6.4MB 上传。**这是第二凶手，不是 drawCall 本身。**

**真凶**：`CONSTRAINTS C1.8` 写「必须 ≤ O(n·k)，k 为邻域常量」——**k 不是常量**。
`CellSize = 3f` 是写死的，格子总数由 `FieldSize = 50` 决定 → 全场约 1111 格、有实体的约 850 格。
- 1000 实体：每格 1.2 个 → 每实体扫 3×3×1.2 ≈ **10 个**邻居
- 100000 实体：每格 118 个 → 每实体扫 3×3×118 ≈ **1062 个**邻居

n 涨 100 倍 × 单次扫描涨 100 倍 = **总迭代量涨 10000 倍**（O(n²/A) 而非 O(n·k)）。
每帧估算：BoidsJob.LocalRoom ≈ 1.06 亿 + ResolveOverlapJob×2 ≈ 2.12 亿 ≈ **3.2 亿次/帧**（1000 实体时约 3.2 万次）。
全是 `NativeParallelMultiHashMap` 的哈希探查 + 距离计算 → **随机内存访问、cache miss 极高**。
**Burst 优化算术与 SIMD，救不了 cache miss。** 这是内存带宽问题不是算术问题。

### 附带发现的第二个坑：初始生成也会卡

`EnemySpawnSystem.SpawnEnemies` 用 100000 × 3 次主线程 `em.SetComponentData`（30 万次 EntityManager 调用），
开局会有数秒级单帧卡顿。此前 2000 实体验证时没暴露。

### 为什么「ECS = 快」的直觉在这里失效

ECS 红利三个前提：① 数据连续（✅ chunk 布局）② Burst + Job（✅ BoidsJob 有 BurstCompile）③ **算法复杂度不退化（❌）**。
常数压到 1/10 救不了量涨 10000 倍。
另注：`InstancedEnemyRenderer` 是 MonoBehaviour，**永远不跑 Burst**，与 ECS 侧无关。

### 这不是 bug，是设计已封顶

C1.1 硬上限 16500（理由是「超过后帧时间非线性上升」）、`ecs-规模与渲染.md §1`「十万是数字不是实体」、
`AGENTS.md` 六宗错里就有「真去模拟十万实体」。10 万 = C1.1 的 6 倍。

### 给出（未实施）的修复方向

- **量级修复**：① `NativeParallelMultiHashMap` → counting-sort bucket 的 uniform grid（连续内存，参考 Unity Physics broadphase）；② CellSize 随规模自适应 / 给每实体设「最多看 N 个邻居就停」的采样上限，让 k 重回常量
- **常数修复**：③ `SolveIterations=2` 改成近场每帧、中景每 2-4 帧摊销；④ `InstancedEnemyRenderer` 用 `IJobParallelFor` 填持久 `NativeArray<Matrix4x4>`，干掉主线程 TRS 循环 + TempJob
- **优先级**：①② 是量级修复（不做就永远上不去），③④ 是常数修复
- 所有数字为代码推算的量级估算，**未实测**（不满足 C1.7，不得当性能结论）。实测路径：Profiler → CPU → Hierarchy 看 `BoidsSystem.OnUpdate` vs `InstancedEnemyRenderer.Update` 各占多少

**未改任何代码**，本轮只做归因。

## 补充：主流做法核实（分场景 vs 单场景）— 结论需分两种「主流」表述

**核实来源**：Unity 官方 DOTS roundtable（Joe Valenzuela Q&A）+ SubScene 官方文档中文转述。

**结论修正**：
- **传统 Unity（GameObject 项目）主流 = 分场景**：MenuScene / GameScene / ResultScene + `LoadScene(Single)`。前提是游戏状态活在 GameObject 层，卸载场景 = 状态清空，边界自洽。所以「主流是单场景」不成立。
- **DOTS 主流 = 一个常驻主场景 + SubScene**。官方立场原话（SubScene 文档）：「ECS 使用子场景而不是场景来管理应用程序的内容。这是因为 Unity 的核心场景系统与 ECS 不兼容。」
- roundtable 里有人问 "ECS is not compatible with multiple scene architecture" 该怎么办，官方答：可以 additive 加载多个 Unity 场景，**但那些场景不含任何 ECS 数据，只有 GameObject/MonoBehaviour**；ECS 数据要作者化进 SubScene 烘焙。Additive 只适合 UI 场景与非 ECS 工作流。

**对本项目的判定**：现状 = 两个普通 Scene（MetaScene/BattleScene）+ 代码 `CreateEntity`。
→ 传统侧丢掉了「卸载即清状态」，DOTS 侧丢掉了「实体与场景绑定的生命周期」，两头不靠。

**阶段策略**：最小闭环阶段「单场景 + 模式」够用；关卡/世界规模上来后再上 SubScene（DOTS 原生流式），而不是再多加一个普通 Scene。

### 头号报错：`IndexOutOfRangeException: ... restricted IJobParallelFor range [0...-1] in ReadWriteBuffer`

栈指向 `BoidsSystem.cs:248`（`GridFillJob` 里 `Entries[slot] = ...`）。
根因：`IJobEntity` + `ScheduleParallel` 往共享缓冲的**任意下标**写，而安全系统默认只允许写「job 自己那个下标」，

→ 已写进 AGENTS.md「七条最容易犯的错」和 ADR-0011 §4。

**这条坑的隐蔽点**：开着 `[BurstCompile]` 时托管安全检查被剥离，**这个异常根本不出现**，
表现成另一种更难查的崩溃。所以「排查期注掉 Burst 换准确托管堆栈」是有效手法，但属性必须补上。

### ⚠ 决定性发现：ADR-0011 初版的 `CellSize` 推导是错的

初版写 `(scan + 0.5) × CellSize ≥ r` → 系数下限 0.667，取 0.7。**这个推导隐含「实体在格子中心」**，
而实体可以贴在格子边缘。

正确条件：格偏移 `floor((a+δ)/s)`，正方向 `sup = 1 + r/s`、负方向 `inf = -r/s`，
落进 `{-1,0,1}` 要求 **`r ≤ s`**，即 **`CellSize ≥ SeparationRadius`（系数 ≥ 1）**。

**症状极隐蔽：自检照样 PASS，只是两个指标同向变差。** 这是靠「两盏灯同时往坏的方向偏」才注意到的：

| 指标 | 哈希表版基线 | factor=0.7 | factor=1.0 |
|---|---|---|---|
| 贴身区两兵最小间距 | 1.13 m | 0.94 m | **1.08 m** |
| 静止 2 秒漂移 | 0.18 m | 0.35 m | **0.19 m** |

改成 1.0 后两个指标回到基线 → 实测证实了推导修正。
**教训：断言宽松度必须和「能力上界」分开想；「PASS」不等于「对」。**

### 线性度验证（核心主张，单独验过）

复杂度 `O(n·k)`，而 `k` 由**密度**决定 → 同一场地加大 n 会退化回 `O(n²/A)`。
要分清「物理必然」与「实现缺陷」，必须做恒定密度对照：

| 组 | 5 万 | 10 万 | 比值 |
|---|---|---|---|
| 固定场地 ±50 | 46.43 ms | 181.07 ms | ×3.90（超线性） |
| **恒定密度 0.13 /m²** | 14.60 ms | 27.87 ms | **×1.91（≈线性）** |

→ **实现是线性的**；固定场地的超线性来自局部密度。

→ 三趟 `8.8×10⁷` 次探查 → 与 181 ms 同量级 ✅

### 决定性结论：不是英雄环带的问题，是**全场超容量**

同一批 10,000 个实体、同一份代码，**只改场地半边长**：

| 场地 | 全场占用率 | 全场最近点对（设计值 1.15 m） |
|---|---|---|
| ±50 | 1.46x | **0.016 m** ❌ |
| ±60.4（容量恰为 10,000） | 1.00x | 0.474 m ⚠ |
| ±120 | 0.25x | **0.968 m** ✅ |

配合规模扫描（±50 场地）：3,000（0.46x）→ 1.051 m；5,000（0.73x）→ 1.033 m；
7,000（1.02x）→ 0.392 m；10,000（1.46x）→ 0.016 m。

**判据：占用 ≤0.75x 健康 / ≈1.0x 临界（0.4~0.5 m）/ ≥1.4x 崩坏（0.02 m 级）。**
±50 场地、1.15 m 间距的物理容量 = **6,858**。

### ⚠ 我上一轮的机制解释是错的，实测把它否掉了

我曾断言「英雄 0.9~2.0 m 环带容量只有 9 个，`PushOutOfHero` 只阻止钻进 0.9 m、

### 另外两条猜测也被实测否掉（留档防重走）

- ✗ **`Entity.Index` 跨 chunk 冲突**：我以为它是 chunk 内索引、跨 chunk 会重复，
  而位置解算靠 `n.Index == selfIndex` 跳过自己 → 同号实体互相视为自己、永不互斥。

### 已落地的修复（三条）

1. **解算器深穿透锁死**（`ResolveOverlapJob.NeighborPush`）：邻居互推是**矢量求和**+整体限幅，
   均匀密实介质里矢量和趋于零 → 「被压到极近的两个兵」这一笔也被抵消，永远分不开。
   修法：把穿透最深的一对独立出来，与平滑项取更优者。
   ⚠ **必须加启动门槛** `DeepPenetrationFactor = 0.4`——第一版没加，健康配置下该在也恒常接管
   （那里穿透只有 0.07 m 而平滑项因对称抵消≈0），1,000 门禁实测：最小间距 0.75 m / 漂移 1.03 m；
   加门槛后回到 **1.09 m / 0.18 m**（与修复前基线一字不差）。
   效果：10,000（1.46x）贴身区最小间距 **0.18 → 0.46 m**。
2. **`ScaleConfig.PhysicalCapacity`** = `π×FieldSize² ÷ ((√3/2)×SeparationRadius²)`，`OnValidate` 超容量报警。
   与 `CellSizeFactor < 1` 的守卫同类：**这种错误不会让自检 FAIL**，只把字悄悄压糊，断言抓不住。
3. **`EcsReadQuery` 域重载 NRE 清掉**：4 个 MonoBehaviour 在**字段初始化器**里 `new(typeof(...))`，
   而 `Type → ComponentType` 的隐式转换要去问 `TypeManager`，域重载时场景对象先于它被构造
   → 每次重载稳定刷 4 条 `NullReferenceException`（栈指向 `TypeManager.cs:1637`）。
   修法：构造函数改收 `Type[]`，转换推迟到首次 `TryGet`。改前 4 条 / 改后 0 条（同一操作序列 A/B 对照）。

## 追加（19:30）：10 万实体四档实测 —— 「支持 10 万吗」的完整答案

### 附带修掉一个真 bug（**非本轮引入**）

`InstancedEnemyRenderer.cs:103` —— 工作区未提交的 ADR-0011 并行化改动把主线程逐元素赋值换成了
`_nativeMatrices.GetSubArray(offset, count).CopyTo(_batchBuffer)`。`CopyTo(T[])` 要求**源与目标等长**，
而 `_batchBuffer` 恒为 `BatchCap`(1023)，于是 `count != 1023` 时每帧抛
`ArgumentException: source and destination length must be the same`。
症状恶劣：**异常先于 `DrawMeshInstanced` 抛出 → 字潮一个都不画 + 每帧刷屏**。
HEAD 版本是逐元素赋值循环，无此约束 → 属并行化改动引入的新缺陷。
修法：`NativeArray<Matrix4x4>.Copy(_nativeMatrices, offset, _batchBuffer, 0, count)`。修后 Play 复跑 0 error。
**教训**：无头自检看不见这个（不跑渲染器），只有真进 Play 才暴露。

## 追加（22:30）：战斗闭环方案设计（尚未写代码，等拍板）

用户要求加战斗：英雄攻击兵（10 血 / 攻击 5 伤 / 英雄 100 血）、兵受击闪白、英雄受击闪红、
英雄持枪前刺动画。**明确要求代码保持结构性、不要为图省事写糙、注意耦合。**

产出：`AIDocs/03-规格/SPEC-0001-战斗闭环.md`（完整 Spec，含文件清单 / 数值提案 / 已知坑 / 阶段划分）。

### 六个关键架构判断（下次别推翻）

1. **伤害事件化 + 单一写入点**：多个生产者（英雄攻击 / 兵接触）写 `NativeQueue<DamageEvent>`，
   `ApplyDamageSystem` 是全工程唯一写 `Health` 的地方。理由：第二处写 Health 出现之后，
   吸血 / 反伤 / 护盾 / 相克倍率要在每个伤害源里重复实现，漏一处就是静默 bug。
2. **命中判定走 O(n) 单中心查询，不复用 SpatialGrid**：以英雄为单中心的查询不是两两邻近查询，
   是 `O(n·1)` 而非 `O(n²)`，不违反 C1.8。把 SpatialGrid 提成跨 System 共享要付生命周期 + 排序依赖代价，
   收益近零。**这是本方案里最重要的一条「反过度工程」判断。** 切换门槛写死：>5000 实体 或 每秒攻击 >10 次。
3. **per-instance 闪白必须升级 `DrawMeshInstancedIndirect` + StructuredBuffer**。
   `DrawMeshInstanced` + MaterialPropertyBlock **做不到 per-instance**（MPB 是整批统一值）。
   选它的真正理由不是闪白本身，而是 C4.5 碎裂序列帧 + C4.2 UV 动画都要同一条 per-instance 通道，
   顺带消掉 C4.3 的 1023 分批限制。`com.unity.entities.graphics` 未安装，不做。
4. **`Health` 用 float 不用 int**：宪法 §2.5 相克倍率（1.0/3.0/0.4）一旦接入，伤害必然是小数；
   用 int 到时要改组件类型 = 波及全部引用。
5. **`BattleProgress` singleton 替代「有没有敌人」的生成判据**：引入死亡后，杀光最后一波会被
   `EnemySpawnSystem` 当成「还没生成」重新刷一整波。顺带承载击杀计数与 HeroDead。
6. **`HeroInput` → `HeroIntent`（Move + Attack）**：现在改名成本 3 处引用，等加了闪避/切字就是几十处。

### 记下的坑

- Space 已被相机视野切换占用 → 攻击键只能另选（拟 J + 鼠标左键）。
- 英雄死亡不要 Destroy 英雄实体（会抖掉依赖 HeroTag 的查询与 Dependency），改 HitDead 冻结判定。
- indirect 三件套：`#pragma target 4.5`（vertex 读 StructuredBuffer）、`material.enableInstancing = true`、
  args buffer 5 个 uint、ComputeBuffer 必须 Dispose。
- 命名的坑（提前避开）：ScriptableObject 叫 `CombatConfig`，ECS singleton 就必须另取名
  `CombatBalance`，否则同命名空间撞名。

### 验证结果

- 编译无 `error CS`

### 实施中撞到并修掉的 3 个真 bug（都是静默型，极难从现象反推）

1. **`SystemAPI.QueryBuilder().Build()` 出来的查询不能手动 Dispose**。我在 `EnemySpawnSystem.ShouldSpawn`
   和 `ApplyDamageSystem.TryGetSingletonEntity` 里都写了 `query.Dispose()` → 抛 `InvalidOperationException`，
   而这个异常发生在**生成实体之前**，现象是「场上一个实体都没有、编译零错误」。
   **它同时打挂了 BoidsSmokeTest**（生成敌人 0/4），这条线索才是定位关键。
   两条所有权规矩相反：`SystemAPI`/`state.GetEntityQuery` 归系统所有**不许 Dispose**；
   `EntityManager.CreateEntityQuery` 归调用者**必须 Dispose**。
2. **`CombatInitSystem` 与 `EnemySpawnSystem` 之间没有排序约束**。只写 `[UpdateBefore(扣血系统)]` 不够——
   生成可能排在初始化之后，第 1 帧英雄血量 0 → 被 `CommitBattleProgressJob` 判死 → `HeroDead=True`
   → **整条战斗链从第一帧起冻结**。六条断言同时失败，看起来像「攻击功能没实现」。
   修法：`[UpdateAfter(typeof(EnemySpawnSystem))]` + 把「未初始化」判据收敛成
   `CombatRules.IsInitialized`（`Health.Max <= 0`）在三处一致使用（初始化 / 伤害结算 / 死亡判定）。
3. **英雄被无差别销毁**。`ApplyPendingDamageJob` 对所有血量归零的实体调 `DestroyEntity`，
   英雄也被销毁了（PlayMode 实测 `heroes=0`、击杀计数 +1）。Spec 里 T6 明确写了不能这么做，
   第一版实现漏了。修法：加 `HeroTags.HasComponent` 守卫，英雄只压血到 0 不销毁。

### 对 Spec 的真实修正（已回填 SPEC-0001 §10）

**`NativeQueue<DamageEvent>` → `PendingDamage` 每实体累加器**。实施时发现两个伤害源的目标集**天然不相交**
（英雄只写兵、兵只写英雄），每个实体的累加器全局只有一个写入方 → 既不需要原子操作也不需要队列。
共享 `NativeQueue` 要付出的生命周期管理与依赖排序是真实复杂度，换来的只是「形式上是事件」的观感。
**代价**：隐含「同一目标集只有一个伤害源」的不变式，只能靠注释约束（写在 `Combat.cs` 的 `PendingDamage` 上）。
将来出现第三个伤害源（环境伤害 / 反伤）时必须回来改这条不变式，而不是就地绕过。

另外三处小偏差：`CombatPhase.cs` 合进 `Combat.cs`；没有独立的 `EnemyDeathSystem`（销毁在 `ApplyDamageSystem`
的 ECB 里）；`HeroView` 未动，武器动画放新增的 `HeroWeaponView`。`HeroRecoverTime` 实际取 0.20 s（Spec 写 0.18）。
